# ADR 0027: 日本語でないクリップは、保存の後で本文を日本語へ置き換える

- ステータス: Accepted
- 日付: 2026-08-29

## 背景

英語の記事をクリップしても、保存されるのは英語のままである。要約は日本語で返るので保存直後は困らないが、後から`read_clip`で読み返すときも、GitHubでファイルを開くときも英語のまま残る。ブラウザの翻訳で読む手もあるが、サイトによって崩れ方が違い、クリップした本文に対しては使えない。

素直にやるなら保存の前に訳すことになるが、それはできない。保存は`save_loaded`の中で起き、その戻りはSlackの返信までの時間に直結する。9万字級の論文（[ADR 0026](0026-one-body-limit-for-fetch-and-reread.md)で実測）を訳し終えるまで返信を止めるのは、このサービスの性格に合わない。

## 決定

### 保存の後で、非同期に置き換える

- `save_loaded`が保存を終えた直後に、翻訳の待ち行列へ「パスと保存直後のSHA」だけの札を1枚投げる。投げるだけなので、クリップの応答時間には出ない。
- 待ち行列は会話用とは別に立てる。会話用は履歴の交錯を避けるため消費を1件ずつ直列にしてあり（[ADR 0008](0008-ai-sdk-and-model-calls-outside-the-durable-object.md)）、ここへ翻訳を混ぜると次のSlackメッセージが翻訳待ちになる。`waitUntil`で保存処理へぶら下げる形も採らない。再試行の仕組みが無く、落ちた翻訳が黙って消える。
- 札を投げるのは保存処理の中の1箇所で、通常BotとMCP Core RPCが合流した後にあたる。入口がどちらでも同じように訳される（[ADR 0021](0021-publish-tools-through-mcp-edge.md)）。

### 訳すかどうかは、本文を読んだAIが渡した言語で決める

- `save_loaded`に省略可能な`body_language`を足す。`load_content`で本文を読んだAIが、観測した事実として渡す。
- 渡すのは「訳すか」ではなく「何語か」にする。日本語へ訳したいのはこのサービスの都合であって、公開`/mcp`の向こうにいるクライアントのAIが決めることではない。事実だけ受け取り、訳すかどうかはこちらのコードで決める形にしておくと、方針を変えるときにコードだけで済む。
- 値が無ければ訳さない。文字の比率からコード側で言語を当てる方法は採らない。コードブロックの多い日本語記事が英語に見えるうえ、「AIが言ったこと」と「コードが判定したこと」のどちらで動いたのかが分からなくなる。訳し漏れはファイルが元の言語のまま残るだけで、同じURLを送り直せば取り直せる。

### 同じファイルの本文を訳文で置き換える

- 訳文は別ファイルにせず、同じパスの本文を置き換える。「1クリップ = 1ファイル = 台帳の1行」の対応が崩れないため、新着一覧、検索、読み直し、削除、片付けのボタンに手が入らない。
- 原文は同じパスの1つ前のコミットに残る。削除を`git revert`で取り返す考え方（README）と同じ形になる。
- フロントマターには`translated_at`を1行足すだけにする。書き戻すときは読んだ項目をそのまま並べ直し、このコードが知らない項目を落とさない。
- **題名とファイル名は変えない。** 保存先のパスは題名から決まる（[ADR 0005](0005-title-based-file-name-and-plain-body.md)）ので、訳題にするとパスが変わり、Slackに出したリンク、片付けボタンが持つパス、台帳の主キーが一斉にずれる。
- 一覧に出る抜粋だけを訳文から作り直す。カードが英語のまま並ぶと一覧としての値が薄いが、題名はファイル名と揃えたままにしたいので、変えるのは抜粋に限る（[ADR 0023](0023-clip-index-cards-and-dismissed-marks.md)）。

### 長い本文は切れ目で分けて訳し、半端なものは残さない

- 本文を見出しと空行の切れ目で塊へ分け、1回あたり英語2万字を上限に詰めて順に訳す。上限に収まる本文はそのまま1つになるので、**普通の記事はモデルを1回呼ぶだけで訳し終わる**。「短ければ一発、長ければ分割」を呼び出し側の分岐にせず、分割する側で吸収する。
- コードブロックの中には切れ目を作らない。途中で割ると囲いの対応が壊れ、訳文の側では直しようがない。
- 2万字という値は**実測ではなく見積もりである**。小さめに倒しているのは外し方が非対称なため。小さすぎれば呼び出しが数回増えるだけだが、大きすぎるとモデルが途中から要約へ切り替わり、痩せた訳文が黙って保存される。
- 出力の上限で打ち切られた応答は失敗として扱い、再試行もしない。同じ本文を投げ直しても同じ場所で切れる。一片でも失敗したら記事ごとやめ、半分だけ日本語のファイルは作らない。
- 書き戻す直前に、読んだファイルのSHAが札のものと一致することを確かめる。違えば後から別の保存が入っているので何もしない。その保存が自分の札を投げているので、訳し直しはそちらに任せる。`translated_at`が既にあるファイルも同じく触らない。

### 訳したことをSlackへ知らせない

要約はもともと日本語で返っている。困るのは後から本文を読むときだけなので、置き換えが済んだことを伝える返信もボタンも出さない。翻訳の結果は`save_loaded`の戻り値にも載せない。

## 検討した代替案

- **保存の前に訳す**: 保存されるものが最初から日本語になり、置き換えも整合の確認も要らない。採らないのは、`save_loaded`の戻りがSlackの返信までの時間に直結するため。長い記事ほど待たされる。
- **文字の比率で言語を判定する**: ツールの契約に触れず、判定がコード側で完結して決定的になる。採らないのは、コードブロックの多い日本語記事が英語に見えるため。読んだAIに聞けばこの弱点は消える。
- **`save_loaded`に`translate`の真偽値を渡す**: 呼ぶ側には分かりやすい。採らないのは、公開`/mcp`の向こうにいるクライアントへ「日本語へ訳したい」というこちらの都合を持たせることになるため。方針を変えるたびに他人のクライアントの挙動に手を伸ばすことになる。
- **訳文を別ファイル（`.ja.md`）へ置く**: 原文をGitHub上でも読める。採らないのは、検索が原文と訳文で二重にヒットし、一覧から除外する処理が要り、削除が2ファイルの話になるため。得られるのは原文の閲覧だけで、原文は元URLでもGitの履歴でも読める。
- **原文の下へ訳文を追記する**: 1ファイルのまま両方を持てる。採らないのは、読み直したときに原文と訳文の両方が会話へ入り、本文の上限（[ADR 0026](0026-one-body-limit-for-fetch-and-reread.md)）を二重に食うため。
- **題名も訳す**: 新着一覧が一番読みやすくなる。採らないのは、ファイル名が題名そのものであるため（ADR 0005）。訳題にするとパスが変わり、既に配ったリンクとボタンが指す先が消える。
- **翻訳にもdead letter queueを置く**: 訳せなかったものを後から拾える。採らないのは、拾って何をするかが無いため。ファイルは元の言語のまま残っているので、気になれば同じURLを送り直せばいい。
- **翻訳専用の失敗ステージを足す**: ログの分類が細かくなる。採らないのは、失敗の内訳がモデル呼び出しとGitHubへの書き込みで、どちらも既存の分類にそのまま乗るため。

## 影響

- **`save_loaded`の引数が1つ増える。** 公開`/mcp`の利用者にも見える。省略できるので、渡さない既存のクライアントは今までどおり動き、翻訳だけが起きない。
- 日本語でない記事をクリップすると、GitHub上のファイルが**保存の数分後に書き換わる**。クリップ直後にリンクを開くと英語で、後から開くと日本語になっている。コミットは1件につき2つ増える。
- 訳文はモデルが書いたものなので、原文と食い違う可能性がある。原文が要るときは、フロントマターの`source_url`か、1つ前のコミットを見る。
- 英語の記事をクリップするたびにモデルの呼び出しが増える。普通の記事で1回、長い論文で数回。
- 新着一覧の抜粋は日本語になるが、題名は原題のまま残る。一覧の中で題名と抜粋の言語が食い違う。
- 待ち行列を1本増やすので、`wrangler queues create`での作成が要る（README、CLAUDE.md）。
- 既に保存済みの英語クリップは訳されない。訳したければ同じURLをもう一度送る。
