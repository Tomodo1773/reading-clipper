# ADR 0026: 本文の上限は取得と読み直しで1つにし、保存時の素性を読み直しにも渡す

- ステータス: Accepted
- 日付: 2026-08-27

## 背景

同じ記事でも、本文が会話へ入る量が経路によって違っていた。

- `load_content`（クリップした流れ）は取得した本文をそのまま返す。上限は `MAX_CONTENT_CHARS = 200_000`。
- `read_clip`（後から保存済みを読み直す）は `MAX_READ_CHARS = 60_000` で頭だけを返す。

60,000という値の根拠は[ADR 0020](0020-search-and-read-saved-clips-via-github.md)に「読み出した本文は会話履歴へ残るため」と記録されている。理由そのものは正しい。しかし**同じ理由は`load_content`にも等しく当たる**。ツールの実行結果はモデルの応答と一緒に `appended` としてDurable Objectの会話履歴へ入り（ADR 0007）、以降のターンでも丸ごと送り直される。取得した本文と読み直した本文で、履歴への残り方は変わらない。

にもかかわらず、片方が200,000で片方が60,000だった。値の差を説明するものは、ADRにもコードのコメントにも無い。コード側の `MAX_READ_CHARS` には説明が一切付いておらず、ADR 0020を読まないと由来にたどり着けない。

差は実害として出ていた。[ADR 0024](0024-arxiv-full-text-from-latexml-html.md)で論文の全文がクリップされるようになり、本文がまるごと入るようになった。cs.CLの最新論文3本の全文テキスト量を実測すると 89,933字 / 29,346字 / 45,077字 だった。3本に1本が60,000字を超える。長いサーベイ論文なら確実に超える。**クリップした直後は論文全体について話せるのに、後から読み直すと後ろが落ちる。**

もう1つ、`read_clip` はフロントマターを読んだ直後に捨てて本文だけを返していた。保存時に分かっていた素性（どこから取ったか、取り切れたか）が、後から読んだAIには一切届かない。返り値には `complete` があるが、これは「読み出しで切ったか」であって、フロントマターの `fetch_complete`（[ADR 0005](0005-title-based-file-name-and-plain-body.md)で「末尾が省略されている」と定義）とは別物である。名前が同じで意味が違うため、`complete: true` を見たAIは「取り切れた本文だ」と解釈しうる。

## 決定

### 上限は1つにする

- `MAX_CONTENT_CHARS = 200_000` を「**1件のクリップの本文が持てる上限**」と定義し直し、取得時と読み直しの両方で使う。`MAX_READ_CHARS` は廃止する。
- 上限を「1回の取得の大きさ」ではなく「1件の記事が会話へ持ち込む量」に対して置く。この形なら、経路が増えても値を増やさずに済む。
- 定数には理由をコメントで書く。ADRを読まないと由来が分からない状態にしない。

### 切ったことは本文に書き残し、切った結果は必ず上限以下にする

- 上限を超えたときの処理を `truncateContent` に1本化する。取得時と読み直しで同じ関数を通す。
- **注記まで含めて上限に収める。** これにより「本文は必ず上限以下」という不変条件が立つ。保存される本文は常に上限以下なので、`read_clip` が保存済みのクリップを読み直しても二度目の切り詰めは起きず、末尾の注記が削れることもない。
- 注記の文面は取得と読み直しで共通にするため「取得内容は」から「本文は」に変える。

### 読み直しにも保存時の素性を渡す

- `read_clip` は本文に加えて、フロントマターの `source_type` と `fetch_complete` を返す。名前は `load_content` が返すものと揃える。
- `complete` は廃止する。読み出しで切ったことは `truncateContent` が本文の末尾へ書くので、それを指す旗を別に立てない。`fetch_complete` との名前の衝突は、片方を消すことで解ける。
- `fetch_complete` は「書かれていない」を `undefined` のまま残す。GitHub上へ手で置かれたファイルには、この行そのものが無い。「取り切れなかった」と「そもそも取得していない」を混ぜると、事実と違うことをAIへ伝える。文字列のまま渡さないのは、`"false"` がコード上は「はい」として扱われるためで、`/mcp` 経由で他人のツールが読む値を逆の意味に読める形で出せない。

## 検討した代替案

- **60,000のまま、理由だけをコメントに書く**: 変更は最小で済む。しかし書ける理由が無い。「会話履歴へ残るため」は`load_content`にも当たり、値の差を説明しない。説明の付かない値に説明を付けたことにするのは、根拠を残すことにならない。
- **`load_content` を60,000へ下げて揃える**: 上限は1つになる。しかしクリップした流れで記事全体について話せることは、このサービスの中心的な価値である（README）。実測で論文の3本に1本が超えるため、揃える方向として下は選べない。
- **`read_clip` の上限を撤廃する**: 保存した本文は既に上限以下なので、自前のクリップでは何も起きない。採らないのは、GitHub上へ直接置かれた大きなMarkdownが `clips/` にあった場合に、そのまま会話へ入るため。上限は自前のクリップでは発動しない**守りの上限**として残す。
- **`read_clip` の返り値を変えず、素性はフロントマターに任せる**: ツール契約に触らずに済む。しかしフロントマターは `read_clip` が捨てているため、このサービスのAIには届かない。届かせる手段が他に無い。
- **`complete` の名前を変えて残す（`body_truncated`など）**: 読み出しで切ったかどうかを機械で読めるようになる。採らないのは、切ったことが既に本文の末尾に書いてあるため。同じ事実を2箇所で言うことになり、読む側にはどちらを見るべきかが増える。

## 影響

- **`read_clip` の返り値の形が変わる。** `complete` が消え、`source` と `fetch_complete` が加わる。`/mcp` 経由の利用者にも同じ変更が見える。出力スキーマは宣言していないため、契約上の破壊はモデルとMCPクライアントの読み方に限られる。
- 読み直しで本文が切れるのは、GitHub上へ直接置かれた200,000字超のMarkdownだけになる。自前のクリップでは発動しない。
- 会話履歴に入りうる本文が、読み直し経路で最大3.3倍になる。長い論文を何本も読み直すスレッドでは、以降のターンで送るトークンが増え、モデルの費用も上がる。これは「後から読み直しても記事全体について話せる」ことと引き換えに受け入れる。
- 切り詰めの注記の文面が変わる（「取得内容は」→「本文は」）。すでに保存済みのクリップの本文は書き換えないため、古いクリップには古い文面が残る。
- `fetch_complete` が `undefined` で返る場合がある。取り切れたかどうかを判定する側は、`false` と「書かれていない」を区別する必要がある。
