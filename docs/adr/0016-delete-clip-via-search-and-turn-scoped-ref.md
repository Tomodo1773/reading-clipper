# ADR 0016: クリップの削除を、検索ツールとターン内の参照番号で組む

- ステータス: Accepted
- 日付: 2026-08-19

> 更新: 検索を経たrefだけで削除する判断は維持する。refをターン内の連番に限定する判断は[ADR 0022](0022-persist-tool-refs-in-durable-object.md)で変更し、ownerに束縛したopaque refを90日保持する。

## 背景

保存が成功しても、中身がゴミになることがある。サイト側の事情で本文が取れず、記事の概要だけ、あるいは同意画面のかけらだけがMarkdownとして残る。取得が途中で切れたことは `fetch_complete` で分かるが、「本文らしきものは返ってきたが記事ではない」はこちらからは判別できない。

このとき「片付ける」を押しても、週次ダイジェストから消えるだけでGitHubリポジトリにはファイルが残る。[ADR 0010](0010-weekly-digest-and-dismiss-bit.md) が決めた `dismissed_at` は読書状態の注釈であって、保存を無かったことにする操作ではない。保存の正本はGitHubにあるのに、その正本を消す手段がどこにも無い。

論点は2つあった。**対象をどう指すか**と、**AIにGitHubを書き換えさせてよいか**である。

## 決定

### 検索ツールを足す

ADR 0010 は、ダイジェストの投稿内容をスレッドの `ThreadAgent` へ書き込むことで「`list_clips` のような追加ツールが要らなくなる」と書いた。これは**対象が必ず会話の中にある**という前提の上に立っている。ダイジェストから片付けるかぎり、前提は成立する。

削除では崩れる。壊れた保存に気づくのはクリップ直後とは限らず、後日GitHubのリポジトリを眺めていて気づくことがある。そのとき対象は会話の中に無い。

`find_clips(query)` を足す。題名・URL・パスの部分一致でD1を引き、件数の上限を切って返す。全文検索の索引は持たない。個人利用の規模では部分一致1本で足りる。

**片付け済みも返す。** ダイジェストの母集団（`dismissed_at IS NULL`）とは絞り方が違う。ゴミだと気づいて一度片付けたクリップを後から消したくなるのが、まさにこの機能の動機だからである。

### 削除ツールは、検索がそのターンで返した参照番号しか受け取らない

保存先パスは記事タイトルそのものである（[ADR 0005](0005-title-based-file-name-and-plain-body.md) / [ADR 0013](0013-flat-clip-storage.md)）。つまりモデルは、記事本文やWeb検索結果に出てきた題名から**実在するパスを組み立てられる**。`set_clip_dismissed` はパスを受け取るが、誤爆しても「戻して」で元に戻るので許容できた。削除では余計なコミットが積まれる。

そこで `delete_clip(ref)` はパスを受け取らない。`find_clips` が返した番号だけを受け取り、ターン内の対応表でパスへ解決する。**組み立てようのない値にする。**

これは `load_content` → `save_loaded`（[ADR 0012](0012-load-content-then-save-loaded.md)）と同じ構造である。あちらも「読んでいないURLは保存できない」を、ツールの説明文ではなくターン内のMapで機械的に止めている。止めているのは常に表のほうで、説明文は守らせるための働きかけでしかない。

**参照番号は永続的なIDではない。** 対応表はWorkerのメモリ上に1ターンの実行中だけ存在し、返信を書き終えれば消える。D1に `id` 列は足さない。永続IDにすると番号が会話履歴に残り、次のターンでも使えてしまう。すると「**消す直前に台帳を引き直した**」という保証が消える。前のターンで見た番号が今も同じ記事を指しているかは、誰も確かめていない。欲しいのは番号そのものではなく、その場で引き直した結果だけが消せるという性質である。安定していることが、この用途では欠点になる。

`find_clips` はパスも返す。既存の `set_clip_dismissed` はパスで引くため、同じ検索から片付けへも繋げられるようにする。削除は番号でしか動かないので、これで削除の安全性は下がらない。

### GitHubを先に消し、D1を後に消す

順番を逆にすると、D1だけ消えてGitHubにファイルが残る。その状態のクリップはダイジェストに二度と出てこないため、**気づく手段の無いゴミ**になる。ADR 0010 が「D1へ登録されないままGitHubにだけ存在するクリップ」として挙げた最悪の不整合を、こちらから作ることになる。

この順なら、途中で落ちて残るのは「ファイルは消えたがD1に行が残る」側である。孤児行はダイジェストに1度出て、「片付ける」を1回押せば終わる。ADR 0010 が既に許容している向きにあたる。

GitHubの削除に失敗したときは、D1を触らずに失敗として返す。**片方だけ消して黙るのが一番悪い。**

### 確認導線を設けない

ADR 0010 は `set_clip_dismissed` について「GitHubを書き換えないうえ、単体のみ・可逆・実行結果が返信に現れる」を根拠に確認導線を設けないと決め、**前提が崩れたら再評価する**と書き残した。削除はこのうち「GitHubを書き換えない」を崩す。

それでも確認導線を設けない。Contents APIのDELETEはコミットを1つ積むだけで、消えるのは既定ブランチの先頭からだけである。本文は1つ前のコミットに残り、`git revert` で戻せる。**可逆性はD1ではなくGitの履歴が担う。** この判断はその一点に依存している。

残る3つは維持する。1回につき1件で、一括を扱うツールは作らない。実行結果は返信に現れる。加えて、検索を経ないと消せないという制約そのものが歯止めになる。モデルの文脈には記事本文とWeb検索結果という第三者のテキストが入っている（[ADR 0006](0006-agent-with-save-tool.md) / [ADR 0009](0009-google-search-grounding.md)）ため、そこから直接パスへ届かないことが効く。

### AIから削除を提案させない

システムプロンプトで、はっきり消してと言われたときだけ実行させる。保存が壊れていそうなときは、その事実だけを伝えさせる。

「片付ける」と「消す」の使い分けも明示する。読まないと決めただけなら片付け、保存そのものが失敗していたなら削除である。内容が期待外れだっただけなら消さない。

## 検討した代替案

- **削除ツールがパスを受け取る**（`set_clip_dismissed` と揃える）: 検索ツールが要らず1手で済む。採らない理由は、保存先パスが記事タイトルそのものなので、モデルが本文中の題名から実在するパスを組み立てられる点。Dismissでは可逆なので許容したが、削除では余計なコミットが積まれる。
- **削除ツールがURLを受け取る**: D1の `url` 列で引けるため、パスよりは組み立てにくい。ただし利用者が毎回URLを手元に持っている必要があり、「あの記事を消して」という呼び方に応えられない。動機に合わない。
- **D1に永続的なIDの列を足す**: 番号が安定し、会話をまたいで指せる。ただしスキーマ変更・手動適用・バックフィルが要るうえ、「消す直前に引き直した」保証が消える。
- **クリップ直後の返信に削除ボタンを並べる**: [ADR 0015](0015-dismiss-button-on-the-clip-reply.md) の仕組みをなぞれば作れる。ただし要約を読んだ瞬間に毎回「片付けか削除か」の判断を迫ることになり、少数の壊れた保存のために全クリップの操作を重くする。入口を増やさないという方針にも反する。
- **D1の行だけ消し、GitHubのファイルは残す**: GitHub Appの書き込み権限を削除に使わずに済む。ただし元の不満（リポジトリにゴミファイルが残る）がそのまま残るので、何も解決しない。
- **消したことを示す行をD1に残す（tombstone）**: 同じURLを再クリップしたときに「一度消した」と伝えられる。ただし読書状態を1ビットに保つ方針を崩し、ダイジェストの問い合わせに条件が増える。消した事実はGitの履歴が持っている。
- **削除の前にボタンで確認する**: 誤爆を確実に止められる。ただしInteractivityの押下処理がもう1本増え、確認待ちの状態をどこかに持つ必要が出る。Gitの履歴で戻せる操作に、それだけの機構を足さない。
- **`fetch_complete` が false のときは保存しない**: そもそもゴミを作らない。ただし途中まで取れた記事は読む価値があることが多く、保存しないほうが損になる。取得が完全かどうかと、保存されたものが記事かどうかは別の問題である。

## 影響

- **AIがGitHubリポジトリを書き換えられるようになる。** これまで書き込みは保存だけで、削除は誰にもできなかった。ADR 0010 が残した「前提が崩れたら確認導線を再評価する」への回答がこのADRにあたる。
- **リポジトリに削除コミットが積まれる。** 本文はその1つ前に残る。クリップの履歴を追うときは、現在のファイル一覧だけでは足りなくなる。
- **検索結果がモデルの文脈に入る。** 題名とURLは記事側から来た第三者のテキストである。件数に上限を切っているが、これまで文脈に入っていなかったものが入るようになる。
- **一覧ツールを持たないという ADR 0010 の判断が部分的に覆る。** `find_clips` はパスも返すため、ダイジェストの外から片付ける経路が事実上増える。
- **Dismissの入口は増えない。** 削除は別の操作として足し、既存のボタンには手を入れない。
- **削除済みのクリップのボタンが古い返信に残る。** 押しても壊れない。押下時にD1へ問い直すため、行が無ければその組がメッセージから消えるだけである（ADR 0015）。
- **同じURLをもう一度送れば保存し直せる。** 片付けの印と違い行ごと消えるので、`dismissed_at` も残らない。
- **D1のスキーマは変わらない。** `schema.sql` の手動適用は不要。
- **Slack AppとGitHub Appの設定は変わらない。** 新しい入口は自然文だけで、Interactivityも増えない。GitHub Appの `Contents: Read and write` は削除にもそのまま使える。
- **1ターンの手数を2手使う。** 検索と削除で、返信を含めて3手になる。`MAX_STEPS` の8には収まるが、同じターンで保存と削除を両方やらせると余裕が減る。
