# ADR 0031: 題名での在否確認は、二次索引ではなくファイル一覧で行う

- ステータス: Accepted
- 日付: 2026-08-31

## 背景

[ADR 0020](0020-search-and-read-saved-clips-via-github.md)は、保存済みクリップの検索母集団をGitHub Code Searchひとつに定めた。本文検索が手に入る一方で、クリップが存在するかどうかの判断まで、この索引ひとつに依存する形になった。

2026-08-26T22:34Z〜08-27T00:27Z を境に、保存先リポジトリのコード検索索引が巻き戻った。その時刻より前に書かれたblobが索引から消え、クリップ39件のうち22件が5日以上検索できない状態になった。ファイル名でも引けず、`in:path`も0件を返した。Git本体は無傷で、欠けていたのは索引だけである。

このときBotは、索引が0件を返したことを根拠に「保存されていない」と利用者へ答えた。実際にはファイルは存在していた。`find_clips`は失敗と0件を`found: []`という同じ形で返すため、モデルには区別する手立てが無い。

復旧の過程で、索引の性質も分かった。ファイルを書き直すと索引へ戻るが、**元と同じ内容へ戻すと再び索引から落ちる**。索引はblobの内容に紐づいており、一度落ちた内容は書き直しでは戻らない。GitHub自身も[2026年4月の可用性レポート](https://github.blog/news-insights/company-news/github-availability-report-april-2026/)で、コード検索索引をGitから派生した二次索引と位置づけ、障害時に「ある時点まで巻き戻して再索引する」と記述している。

つまりコード検索索引は、内容が揃っていることを保証しない部品である。ADR 0020 はそれを唯一の母集団に据えていた。

## 決定

### 題名での在否確認を、ファイル一覧から行う

`list_clips(title_query?)`を追加する。

- 母集団は`GET /repos/{owner}/{repo}/git/trees/HEAD:clips`が返すファイル一覧。1リクエストで`clips/`直下の全件が返る。二次索引を経由しない。
- `title_query`を省略すると全件が対象。渡すと題名で絞り込む。
- 成功時は必ず`matched`（該当数）を返す。**`matched`があること自体が、全件を走査した証拠になる。**
- `matched === 0`は「その題名では保存されていない」という事実として扱ってよい。
- 失敗時は`matched`を返さず`failed_at`を返す。0件と、見に行けなかったことが、形として別物になる。
- ツリーが`truncated`を返したときは失敗として扱う。全件を見ていない以上、`matched`を名乗ってはならない。`searchGitHubCode`が`incomplete_results`を失敗とするのと同じ規則である。

### 該当が多すぎるときは、切らずに件数を返す

該当が100件を超えるときは、項目を返さず`matched`と`too_many`だけを返す。任意の一部を返すことは、利用者にもモデルにも「それが全部だ」と誤らせる。

100という値は、1件あたり約400バイト・1回のツール応答の予算を約40KBとして置いたものである。**これはガードではなく機能上限であり、有限の寿命を持つ。** 現在の保存ペース（1日3件・39件時点）では、クエリ無しの全件列挙が成立するのは概ね3週間である。それ以降、`list_clips()`は「件数と絞り込みの要求」を返すようになる。これを劣化とは見なさない。蔵書が数百件あるときに「全部見せて」へ数百件を返すのは、Slackの応答としても文脈の使い方としても誤りだからである。

### 題名の照合は、両辺に同じ粗いキーを掛ける

検索語とファイル名の双方へ同じキー関数を掛け、検索語を空白で割って全語の部分一致（AND）で判定する。

```
NFKC正規化 → 小文字化 → 英数字・仮名・漢字以外の連続を空白1つへ → trim
```

`makeClipFileName`の逆写像は作らない。ファイル名は`<>:"/\|?*`を空白へ置換してから`-`へ畳むため、利用者が本物の題名を貼ると記号が食い違う。保存済み39件のうち9件が該当する。

- 題名: `AI-Native な開発の実践に向けて | メルカリエンジニアリング`
- ファイル名: `AI-Native-な開発の実践に向けて-メルカリエンジニアリング.md`

NFKCだけでは足りない。`〜`(U+301C)と`～`(U+FF5E)はNFKCで統一されず、保存済みの2件がU+301Cを含む。記号をすべて区切りへ落とすことで、この差と全角・半角の揺れをまとめて吸収する。

### 並び順は既存の規則に揃える

`clipped_at`の新しい順、同着は`path`昇順。`selectRecentClips`の`ORDER BY clipped_at DESC, path ASC`と同じである。D1に行が無いクリップは`clipped_at`を持たないため末尾に来る。

母集団は権威あるファイル一覧、順序は既存規則、というのがここでの分担である。D1は[ADR 0020](0020-search-and-read-saved-clips-via-github.md)のとおり注釈のままで、母集団にはしない。

### `find_clips`は挙動を変えない

本文検索はコード検索索引に依存したままにする。変えるのは説明文だけで、0件が保存されていないことの根拠にならないことと、題名で確かめるなら`list_clips`を使うことを書く。

## 検討した代替案

- **`find_clips`にファイル名照合を混ぜ、和集合を返す**: ツールが1つで済む。採らない理由は、2つの母集団で**0件の意味が違う**ため。片方は全件走査の結果、もう片方は外部索引の返答である。1つの`found`へ混ぜると強い0件と弱い0件が区別できなくなり、今回の事故と同じ状態に戻る。順位付けの共通尺度が無く、上位N件の決め方も恣意的になる。
- **D1を母集団にして題名・URLを検索する**: URLでも引ける。採らない理由は[ADR 0020](0020-search-and-read-saved-clips-via-github.md)と同じで、GitHubへの保存に成功してD1への記録に失敗したクリップが検索から永久に抜けるため。
- **自前の全文索引を持つ**: 本文検索も索引障害から独立する。採らない理由は、[ADR 0020](0020-search-and-read-saved-clips-via-github.md)が退けた母集団の同期問題がそのまま戻るため。今回は「名前を言えるものは必ず見つかる」という床を作るに留める。
- **Contents API でディレクトリを引く**: `html_url`が得られる。採らない理由は1ディレクトリ1000件の上限があるため。現在39件だが、1日3件のペースでは1年以内に到達する。
- **ルートツリーの再帰取得（`?recursive=1`）**: 1リクエストで済む。採らない理由は、保存先が汎用の私物リポジトリで、`clips/`と無関係なディレクトリが増えると毎回の取得量が連動するため。
- **ページ送りを持つ**: 全件列挙の寿命が延びる。採らない理由は[ADR 0020](0020-search-and-read-saved-clips-via-github.md)の「続きが要るときは語を絞って探し直す」と揃えるため。エージェントにページ送りのループを回させると、途中で打ち切った結果を全体として扱う失敗が入りやすい。

## 影響

- 題名を言えるクリップは、コード検索索引の状態によらず必ず見つかる。索引が欠けていても在否の判断ができる。
- 「見つからなかった」と「見に行けなかった」が、ツールの戻り値の形で区別できる。今回のように存在するクリップを「保存されていない」と断定する失敗は起きない。
- **本文にしか出ない語での検索は、今までどおりコード検索索引に依存する。** 今回消えた22件は本文検索では引けなかった。床は上がるが天井は上がらない。
- ファイル名は255バイトで切り詰められる（`MAX_FILE_NAME_BYTES`）。長い題名では末尾の語で引けず、`matched === 0`が偽になりうる。ツールの説明文に明記する。現在の最長は176バイトである。
- `list_clips`は`github_url`と`snippet`を返さない。ツリーは`html_url`を返さず、自前で組み立てるとコード検索由来のcommit固定URLと形の違うリンクが同じ意味で並ぶためである。
- クリップのURLで探す手段は増えない。ファイル名にURLは含まれず、D1のURL列で照合すると、D1に行が無いクリップだけ引けないという保証の弱い経路が同じツールに混ざる。別の要求として切り離す。
