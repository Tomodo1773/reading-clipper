# ADR 0030: 新着一覧を、公開境界Workerの読み取り専用ページとしても出す

- ステータス: Accepted
- 日付: 2026-08-31

## 背景

ADR 0017と0023で、`clips/README.md`を「自分から見に行って眺める棚」として設計した。運用してみると、その棚がいちばん見たい場面で開けない。

- GitHubのURLを開かないと見られない
- 中身をMarkdownとして読むことになる
- 保存先はprivateリポジトリなので、GitHubにログインできない環境（会社のPCなど）では開けない

一方、一覧に出している材料（題名、元記事のURL、抜粋、サムネイル、保存日、片付けの印）はすべてD1にある。GitHubのREADMEは、そこから毎回全体を作り直している派生ビューにすぎない（ADR 0017）。同じ材料から別の見え方を出すことに、新しいデータは要らない。

## 決定

### 公開しない。既存のAccessで自分だけが見る

- 新しい認証の仕組みを作らない。MCP Edgeを保護しているCloudflare Accessのアプリケーションに、そのまま相乗りする。
- 許可するのは自分の個人メールアドレスだけにする。one-time PINは「ログイン時にそのメールボックスを読めること」しか要求しないため、会社のPCからでも個人アドレスで通る。**会社のメールアドレスを許可リストへ足さない。** 足すと、この一覧を開く鍵の所有者に会社が加わる。
- 公開しないので、抜粋やサムネイルが第三者へ再配布されることは起きない。出す内容をGitHub版から削らない。

### 静的ファイルを書き出さず、リクエストのたびにD1から組み立てる

- 書き出すと、同じデータから「D1→GitHubのREADME」と「D1→静的ファイル」の2本の生成経路を持つことになる。どちらもベストエフォートで失敗しうるので、片方だけ古い状態が新しく生まれる。
- 都度組み立てれば同期経路はゼロで、常に最新になる。読むのはD1の2クエリだけで、READMEを作り直すときと同じものを使う。

### 母集団と並びはREADMEと揃える

- 最新20件、片付け済みも含む（ADR 0017、ADR 0023）。閲覧ページのために選び直さない。
- 「本当に見たいのは最近の20件ではなく、片付けていない在庫のほうではないか」という疑問は残っている。ただしそれは新着一覧そのものの定義を変える話で、変えるならGitHub側と一緒に変える。**片方だけ範囲を変えると、同じ名前の一覧がGitHubとWebで食い違っていく。**

### 公開境界Workerへ相乗りし、画面の組み立てはCoreへ置く

- 3つ目のWorkerを立てない。Custom Domain、Accessアプリケーション、Workers BuildsのGit接続（ダッシュボードでしか作れない）がもう一式増える。個人の読書一覧1枚に対して重い。
- Slackを受けるCoreのホスト名にAccessを掛けない。Slackの受け口が認証の後ろへ入る構図を作らない。
- **Edgeは認証の確認と受け渡しだけを持つ。** HTMLはCoreが組み立ててRPCで返す。Edgeにデータもsecretも増えず、ADR 0021の「公開境界に業務secretを置かない」がそのまま保たれる。Coreは既にMarkdownという表示形式を持っているので、HTMLもその隣に置く。
- **ツール契約には載せない。** `callTool`は外部MCPクライアントへ公開するツールを通す口である。画面のための取得をそこへ足すと、別のSlack Botに「一覧を返すツール」が生えてしまう。RPCの別メソッドにする。
- 監査情報の`source`に`web`を足す。これは「Accessを通った呼び出しである」ことの印で、認可には使わない。**値によって処理を分けない。**

### レイアウトはMarkdown版と共有しない

- カード5件＋それ以前は箇条書き、という振り分けは、GitHubが表の各セルへ罫線を引くことから出た形である（ADR 0023）。自分で配信するHTMLにその制約は無い。
- 共有するのは、データの形（エントリと件数）と、**片付け済みを一覧から消さず印として出す**という方針だけにする。並べ方は各出力が自分で決める。HTML側は20件を1つのリストとして、サムネイルと抜粋を添えて並べ、片付け済みは薄くして取り消し線を引く。

### 操作は置かない

読み取り専用にする。片付けボタンを出さない。閲覧の入口はWebにも増えるが、**操作がSlackだけで完結する**という設計は変えない。

### エスケープの意味が変わることを、コードに書き残す

抜粋と画像URLのエスケープは、GitHubのREADMEでは表示崩れの防止でしかなかった（ADR 0023）。GitHubのサニタイザが後ろにいるためである。自分で配信するページにはそれが無く、**同じ関数が注入への防御そのものになる。** 属性値は必ず`"`で囲み、URLは`http`/`https`だけを通す既存の判定を経由させる。

## 検討した代替案

- **GitHub Pagesで`clips/`を公開する**: 追加のWorkerは要らない。ただし公開範囲がリポジトリの状態そのものになり、本文の正本を置いた場所をアプリ以外の経路の変更ごと公開することになる。「一覧だけ公開したい」が「本文も公開しうる」に化ける。
- **アプリから静的ファイルを書き出して配信する**: 最初に考えた形。生成経路が2本になり、片方だけ古い状態が生まれる。都度組み立てれば起きない問題を、わざわざ作ることになる。
- **3つ目のWorkerを立てる**: 役割の分離としては綺麗で、ホスト名も用途に合う。ただしWorkers BuildsのGit接続が手作業で1つ増える。後から切り出すほうが、畳むより安い。
- **CoreのWorkerへ直接ページを置く**: RPCが要らず最短だが、Slackの受け口と同じホスト名になる。Accessをパスで除外する設定に頼ることになり、設定の誤りがSlackの受付に直結する。
- **Edge側でHTMLを組み立てる**: RPCはデータだけを運ぶ形。ただしEdgeへエスケープ、URL検証、表示用のテストが増え、「変換だけを持つ」という役割から外れる。CoreにはMarkdownのレンダラとそのテストの土台が既にある。
- **完全に公開する**: 認証が要らず最も手軽。ただし抜粋は記事本文の一部（翻訳済みのクリップでは機械翻訳された二次的著作物）で、Xのポストのように短い原著では抜粋が全文に近くなる。加えて、何をいつ読んでいるかの時系列そのものが個人情報に近い。得られる手軽さに見合わない。
- **会社のメールアドレスも許可する**: 会社のPCで受け取りやすくなる。しかしone-time PINはデバイスを問わないため、そもそも必要がない。許可すれば鍵が1つ増え、その鍵は会社が管理する。

## 影響

- **Accessアプリケーションのセッション長が、MCPクライアントと共通になる。** ブラウザで開き直す頻度を下げるために延ばすと、Managed OAuthを通っている別のSlack Bot側のセッションも一緒に延びる。単一利用者の個人サービスなので受け入れる。
- `MCP_HOSTNAME`という名前が実態とズレる。あのWorkerは「MCP専用」ではなく「公開境界」になった。secretの改名には手作業が伴うため、名前は据え置く。
- `getIdentity()`がページ表示のたびに1回走る。MCPのツール呼び出しと同じコストだが、リロードのたびに掛かる。
- MCP Edgeが`/mcp`以外のパスを持つ。HostとOriginの検証は両方の入口へ同じように掛ける。Originヘッダを持たないリクエストは通る実装なので、ブラウザの通常の遷移はそのまま抜ける。
- 保存済みMarkdownへの「GitHub版」リンクは、GitHubのblob URLになる（refは`HEAD`にして、既定ブランチ名を設定として持たない）。privateリポジトリなので、GitHubにログインできない環境では開けない。一覧を眺めること自体は成立するので許容する。
- Webから「読んだ」「片付けた」はできない。片付けはSlackのボタンか会話で行う。
