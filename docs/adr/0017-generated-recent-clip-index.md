# ADR 0017: フラットな保存構造と新着順の表示を分離する

- ステータス: Accepted
- 日付: 2026-08-19

## 背景

ADR 0013で、クリップは`clips/{記事タイトル}.md`へフラットに保存すると決めた。ホストや分類をフォルダへ持たないため、GitHub上でタイトルから横断して探しやすい。一方、GitHubのファイル一覧は名前順なので、件数が増えると最近保存した記事がどこにあるか分からない。

ファイル名へ日付を付ければ名前順を時間順にできるが、意味の中心であるタイトルが読みづらくなる。年月フォルダも新着の場所は示せるが、横断して探すたびにフォルダをまたぐことになり、ADR 0013の判断を戻してしまう。

## 決定

- 記事の保存先は`clips/{記事タイトル}.md`のまま変えない。
- `clips/README.md`を、最近保存した20件の派生ビューとしてWorkerが自動生成する。GitHubがフォルダのREADMEを自動表示するため、別の画面や操作は増やさない。
- 一覧はD1の`clipped_at DESC, path ASC`で決める。片付けは表示順と別の注釈なので、`dismissed_at`では絞らない。同じ記事を保存し直しても`clipped_at`は更新しないため、新着へ戻さない。
- 各行にはJSTの`M/D`、元記事へのリンクにしたタイトル、URLから取ったホストを出す。人が一覧から読むときの主な遷移先は保存済みMarkdownではなく元サイトである。URLが無い、または不正な古いデータはタイトルをリンクにしない。日付は表示にだけ使い、ファイル名には埋め込まない。
- READMEは追記せず、D1から毎回全体を作り直す。並びの崩れと同じ項目の重複を持ち越さないためである。
- 記事の保存または削除とREADMEの更新は、Contents APIの別コミットにする。既存の単一ファイル保存をGit Data APIへ置き換えるほどの原子性は要らない。README更新の失敗はログへ残すが、先に成立した記事本体の操作は失敗扱いにしない。
- READMEのSHAが409で競合した場合は、最新のSHAとD1を読み直して1回だけ再試行する。通常のQueue処理は`max_concurrency: 1`で直列だが、対象リポジトリを外から編集した場合の競合は残るためである。
- 生成READMEには所有を示すコメントを入れる。既存の`clips/README.md`にそのコメントが無ければ上書きしない。記事タイトルの`README`は大文字小文字を問わず`README-clip.md`へ保存する。
- D1のバックフィルは、所有コメントを持つ`clips/README.md`だけを記事の母集団から外す。手書きREADMEや過去に同名で保存された記事を、名前だけで黙って除外しない。

## 検討した代替案

- **ファイル名へ日付prefixを付ける**: 追加ファイルは要らないが、すべての名前が長くなり、タイトルから探す体験を恒久的に悪くする。
- **年月フォルダへ分ける**: 時系列は構造だけで分かるが、横断閲覧のためにフラット化したADR 0013と反対方向になる。
- **Slackへ新着一覧ツールを足す**: D1だけで実装できるが、GitHubでクリップを直接眺めるときの問題は残る。
- **Git Data APIで記事とREADMEを1コミットにする**: 原子的に更新できるが、ref、tree、commitの管理と競合処理が保存・削除の全経路へ増える。失敗しても再生成できる派生ビューには重すぎる。

## 影響

- 1回の保存または削除につき、README更新のコミットが1つ増える。
- GitHubの更新に成功してD1の更新に失敗したクリップは、新着一覧へ出ない。これは週次ダイジェストと同じ既存の不整合で、バックフィルを流せばD1側を復旧できる。
- GitHubから手で記事を削除してD1に孤児行が残ると、READMEにも壊れたリンクが残りうる。実行時にGitHubの全ファイルと突き合わせる処理は追加しない。
- デプロイ時点ではREADMEを作らない。次の保存または削除で初めて生成する。
- 既存の`clips/README.md`は自動移動しない。所有コメントが無い場合は安全側に倒して更新を止めるため、導入前に必要なら手で退避する。
