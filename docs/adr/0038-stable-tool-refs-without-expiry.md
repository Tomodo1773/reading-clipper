# ADR 0038: ツール参照を、取得した本文はURLごと、クリップはパスごとに固定し、期限を持たない

- ステータス: Accepted
- 日付: 2026-11-24

## 背景

[ADR 0022](0022-persist-tool-refs-in-durable-object.md)は、`load_content`と`find_clips` / `list_clips`が呼ばれるたびにランダムなrefを新しく発行し、`ToolState`に90日保持してAlarmで消すと決めた。

この方式には次の問題があった。

- 同じURLを2回読むと本文が2行になり、どちらも90日残る。保存先の記事ごとに本文が1つという形になっていない。
- 同じクリップを検索するたびにrefが増える。
- 期限、Alarmの再設定、期限切れの判定を実装して保守する必要がある。そのテストに書いた固定日付が90日後の2026-11-23を過ぎ、mainのCIが落ちた。

ADR 0022が90日の根拠にしたのは、Slack無料プランで会話が見える期間である。これは会話履歴（`ThreadAgent`）の保持期間であって、本文やクリップへの参照まで同じ期限にする理由にはならない。

## 決定

`ToolState`に2つの表を持つ。

| 表 | キー | 中身 |
| --- | --- | --- |
| `loaded` | 取得した記事のcanonical URL | ref、取得した本文（`FetchedContent`） |
| `clips` | 保存先パス | ref、題名 |

- refは行を作るときに1回だけ発行し、以後変えない。
- 同じURLを読み直したら本文だけ最新に差し替え、refは同じものを返す。
- 同じパスを検索・一覧したら題名だけ最新にし、refは同じものを返す。
- 期限を持たず、Alarmで消さない。
- 表を分けたまま、`loaded`のrefは`save_loaded`だけ、`clips`のrefは`read_clip` / `delete_clip`だけが受け付ける。取得した本文の題名を既存のクリップと同じにすれば、そのパスへのrefが手に入ってしまう。表を分けることで、[ADR 0016](0016-delete-clip-via-search-and-turn-scoped-ref.md)の「検索を経たrefでしか消せない」を保つ。
- ツール名、引数名（`loaded_ref` / `clip_ref`）、返り値の形は変えない。`ref_error`は`unknown_ref`だけになる。

移行のための掃除コードは書かない。一度しか動かないコードを本番に残さないためである。

- 旧表`tool_refs`は使われないまま残る。中身は直近90日に取得した本文とクリップのrefで、どこからも読まれない。
- 予約済みのAlarmは1回だけ届く。`ToolState`は`alarm()`を持たないので何もせず終わり、再予約もされない（ローカルのworkerdで、ハンドラの無いクラスへのAlarmがエラーにならず消えることを確認した）。
- 既存の会話に残る旧refは`unknown_ref`になり、モデルは読み直すか探し直す。

### 容量

本文は1件あたり最大20万文字（UTF-8で最大約600KB）で、SQLiteの行サイズ上限8MBに収まる。Durable Objectのストレージは、Freeプランではアカウント全体で5GBである。オブジェクトごとの上限は、limitsページの表では10GB、同じページのFAQでは「Freeでは1GB」と書かれていて一致しない。少ないほうの1GBで見積もっても、1件50KBなら約2万件入る。個人利用の取得数ではこの範囲に収まるため、消す仕組みは持たない。上限に近づいたら、保存済みの記事の本文から消す（正本はGitHubにある）。

根拠:

- [Durable Objects limits](https://developers.cloudflare.com/durable-objects/platform/limits/)
- [Durable Objects pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)

## 検討した代替案

- **ADR 0022のまま、テストの日付だけ直す**: CIは直るが、同じ記事の本文が取得のたびに増える形と、期限・Alarmの保守が残る。
- **1つの表にまとめ、記事ごとに1つのrefで保存・読取・削除をすべて扱う**: refは1種類で済む。ただし取得した本文の題名を既存クリップと同じにすれば削除できるrefが手に入り、ADR 0016の制約が崩れる。
- **refをやめ、`save_loaded`にURL、`read_clip` / `delete_clip`にパスを渡す**: 発行が要らない。ただし削除はモデルが題名から組み立てたパスで動いてしまう（ADR 0016）。
- **期限を残し、保存済みのものだけ消す**: 容量は減るが、期限とAlarmの仕組みは残る。

## 影響

- 同じURLのrefは、読み直しても会話をまたいでも同じものになる。
- 取得した本文は、保存したかどうかにかかわらず消えずに残る。容量は上記の範囲で見る。
- 期限切れによる`expired`、種類違いによる`wrong_kind`はなくなる。
- 同じURLの本文を読み直すと、前の本文は上書きされる。古い本文を保存する手段はない。
- ADR 0022のうち、「refを90日保持する」「Alarmで消す」「同じURLでも新しいrefを発行し、過去のsnapshotを上書きしない」をこのADRで置き換える。会話履歴の90日保持はADR 0022のまま変えない。
