# ADR 0015: クリップ直後の返信にDismissボタンを出し、その有無をツールの実行結果で決める

- ステータス: Accepted
- 日付: 2026-08-19

## 背景

[ADR 0010](0010-weekly-digest-and-dismiss-bit.md) はDismissの入口を2つ用意した。週次ダイジェストの行ごとのボタンと、スレッドでの自然文である。

運用してみると、「これはもういい」と判断できるのは**クリップした直後**、AIの要約を読んだその瞬間であることが多い。ところがその瞬間に押せるものが無く、片付けるには日曜のダイジェストを待つか、自分で文章を打つしかない。ボタンという最も軽い操作が、最も判断しやすい時点で使えていない。

ボタンそのものは ADR 0010 の実装をなぞれば作れる。設計上の論点は**それをどこに出すか**である。クリップするのはエージェントなので、保存が起きた返信と、雑談や質問に答えただけの返信とを、何をもって区別するのかが決まっていなかった。

## 決定

### ボタンの有無は`save_loaded`の実行結果で決める

保存が起きたかどうかは、モデルが返事を書くより前に確定している。AI SDKは1ターンぶんの実行結果として、そのターンで呼ばれたツールの結果を `staticToolResults` に持つ。ここに入るのはモデルが書いた文字列ではなく、`save_loaded` 自身が `return` したオブジェクトである。

したがって判定は「そのターンで `save_loaded` が成功を返したか」という機械的な条件になる。**返信の文面は一切見ない。** プロンプトへの追記も要らない。

これは ADR 0010 の「`action_id` と `value` で意図が確定して届くものを、自然文へ落として再解釈させない」の裏返しにあたる。あちらは入力側の話で、こちらは出力側の話だが、確定した構造を散文に落として読み直さないという判断は同じである。

読むのは `staticToolResults` であって `toolResults` ではない。前者は全ステップぶんが入るが、後者は最終ステップだけなので、保存の後にモデルがもう1手を挟んだターンで取りこぼす。

結果として、ボタンは保存が起きたターンの返信にだけ付く。雑談の返信にも、同じスレッドで後から記事について質問した返信にも、保存が失敗した回にも付かない。

### `action_id`をダイジェストと分ける

ダイジェストは `dismiss_clip`、返信は `dismiss_thread_clip` とし、押下処理も分ける。

**これは見た目の都合ではない。** ダイジェスト側の押下処理は、メッセージを見出しと `clip-N` の組へ組み直したうえで、まだ片付いていない行だけを残す。同じ `action_id` で返信メッセージから押下が届くと、その組み直しが返事の本文ごと消してしまう。2つのメッセージは形が違うので、処理も分ける。

### 押した後は一行に差し替える。トグルにしない

押されたクリップの `actions` ブロックを、`片付けた` の `context` ブロックへ差し替える。ダイジェストが押された行を消すのと同じ考え方で、メッセージに「どちらの状態か」を持たせない。

取り消しは、スレッドで「戻して」と言えば既存の `set_clip_dismissed` に `false` が渡る。ADR 0010 が「戻したいときは会話で戻す」と決めたとおりで、入口を増やさない。

差し替え先をD1へ問い直さない点はダイジェストと異なる。1つの返信が持つのは自分が保存したクリップだけで、押した組以外に触れないため、続けて押しても他の行が書き戻る事故が起きない。

### 台帳に行が無いときは、そう言う

`setClipDismissed` はそのパスが `clips` テーブルにあったかどうかを返す。無ければ `片付けた` ではなく、台帳に無い旨へ差し替える。

GitHubへの保存は成功したがD1の記録に失敗したクリップがこれにあたる。ADR 0010 は「D1へ登録されないままGitHubにだけ存在するクリップはダイジェストに永久に出てこない」「この不整合を検出する手段は持たない」と書いたが、**この経路で初めて目に見えるようになる。**

### 再送に備えて保存したパスを永続化する

`ThreadAgent` の `handled` テーブルは返信の文面だけを持っていた。Slackへの投稿だけが失敗して再送になったとき、モデルは動かさず記録した返信を投げ直すため、このままでは**その回だけボタンが落ちる**。

`handled_clips(event_id, path, title)` を足し、そのターンで保存できたクリップを返信と一緒に残す。`handled` へ列を足さないのは、既に存在するDurable Objectには `CREATE TABLE IF NOT EXISTS` が効かず `ALTER` が要るためで、表を分ければコンストラクタの既存の書き方のままで済む。

## 検討した代替案

- **返信の文中にマーカーを書かせて拾う**（`[[dismiss:パス]]` のような）: プロンプトを1行足すだけで実装できる。採らない理由は、モデルが書き忘れる／存在しないパスを組み立てるという失敗モードが増えるうえ、既に構造として持っている情報をわざわざ散文に落として読み直す形になるため。ADR 0010 が退けた「ボタン押下を自然文へ落としてAIへ渡す」と同じ筋の悪さがある。
- **「ボタンを出す」ツールをモデルに持たせる**: 判断をモデルに委ねられる。ただしステップが1手増え、「AIがツールを呼ばない」失敗モードが乗るだけで、得られる情報は `save_loaded` の結果と同じである。
- **受付の時点でURLの有無を見て分岐する**: [ADR 0006](0006-agent-with-save-tool.md) の「入力を事前分類しない」に正面から反する。その時点では保存先のパスも、そもそも保存するかどうかも決まっていない。
- **ボタンを別メッセージとして投稿する**: 返信をブロック形式にせずに済む。ただしスレッドの投稿数が倍になり、どの返信に対応するボタンなのかが読み取りづらくなる。
- **押した後を「戻す」ボタンにしてトグルにする**: 取り消しが1タップで済む。ただしメッセージが状態を持つことになり、ダイジェスト側の挙動と揃わなくなる。取り消しの導線は会話に既にある。
- **1つの`actions`ブロックにボタンを並べる**: 複数保存したときのブロック数が減る。ただし押されたものだけを差し替えるのに、ブロックの中身を作り替える必要が出る。1件につき1ブロックなら、そのブロックごと置き換えるだけで済む。

## 影響

- **Dismissの入口が3つになる。** ダイジェストのボタン、返信のボタン、スレッドの自然文。いずれも `setClipDismissed` の1本に集約されるため、状態の持ち方は増えない。
- **D1へ記録されなかったクリップの不整合が、初めて利用者から見える。** 検出手段が無いという ADR 0010 の状況は変わらないが、押したときに気づける経路ができた。
- **同じ記事を同じスレッドで2回送ると、古い返信のボタンが残る。** 上書き保存になるため両方のボタンが同じパスを指す。片方を押した後にもう片方を押しても、同じ状態を書き直すだけで壊れない。ダイジェストのようにD1へ問い直して掃除することはしない。
- **返信がブロック形式の投稿になる。** 保存が起きた回だけで、雑談の返信は今までどおりテキストのみ。通知に出る文とブロックを読めないクライアント向けの `text` には、これまでどおり返信全文を入れる。
- **返信本文が3000文字を超えるとsectionに収まらない。** 超える場合は複数のsectionへ分割する。保存直後の返信は60〜120字に収める指示があるため通常は起きないが、超えると `invalid_blocks` でメッセージ全体が拒否されるので、投げる前にこちらで割る。
- **Slack Appの設定変更は要らない。** Interactivityの入口は ADR 0014 で `/slack/events` 1本に集約済みで、スコープの追加も再インストールも発生しない。
- **D1のスキーマは変わらない。** 足すのはDurable Object側の表だけで、`schema.sql` の手動適用は不要。
- **`ThreadAgent`の`save`の引数が増える。** 既存の呼び出し側は1か所だけで、省略時は空として扱う。過去に記録された `handled` の行はクリップを持たないため、その再送ではテキストのみが投稿される。
