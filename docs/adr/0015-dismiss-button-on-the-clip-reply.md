# ADR 0015: クリップ直後の返信にもDismissボタンを出し、押下の経路をダイジェストと1本に統合する

- ステータス: Accepted
- 日付: 2026-08-19

## 背景

[ADR 0010](0010-weekly-digest-and-dismiss-bit.md) はDismissの入口を2つ用意した。週次ダイジェストの行ごとのボタンと、スレッドでの自然文である。

運用してみると、「これはもういい」と判断できるのは**クリップした直後**、AIの要約を読んだその瞬間であることが多い。ところがその瞬間に押せるものが無く、片付けるには日曜のダイジェストを待つか、自分で文章を打つしかない。ボタンという最も軽い操作が、最も判断しやすい時点で使えていない。

ボタンそのものは ADR 0010 の実装をなぞれば作れる。設計上の論点は2つあった。**どこに出すか**（クリップするのはエージェントなので、保存が起きた返信と雑談の返信をどう区別するか）と、**既存のダイジェストの押下処理とどういう関係に置くか**である。

## 決定

### ボタンの有無は`save_loaded`の実行結果で決める

保存が起きたかどうかは、モデルが返事を書くより前に確定している。AI SDKは1ターンぶんの実行結果として、そのターンで呼ばれたツールの結果を `staticToolResults` に持つ。ここに入るのはモデルが書いた文字列ではなく、`save_loaded` 自身が `return` したオブジェクトである。

したがって判定は「そのターンで `save_loaded` が成功を返したか」という機械的な条件になる。**返信の文面は一切見ない。** プロンプトへの追記も要らない。

これは ADR 0010 の「`action_id` と `value` で意図が確定して届くものを、自然文へ落として再解釈させない」の裏返しにあたる。あちらは入力側の話で、こちらは出力側の話だが、確定した構造を散文に落として読み直さないという判断は同じである。

読むのは `staticToolResults` であって `toolResults` ではない。前者は全ステップぶんが入るが、後者は最終ステップだけなので、保存の後にモデルがもう1手を挟んだターンで取りこぼす。

結果として、ボタンは保存が起きたターンの返信にだけ付く。雑談の返信にも、同じスレッドで後から記事について質問した返信にも、保存が失敗した回にも付かない。

### 押下の経路をダイジェストと1本にする

ダイジェストの行と返信のボタンは、**同じ `action_id` の同じボタン**にし、押下処理も1つにする。

当初は返信用に別の `action_id` と別の押下処理を作った。ダイジェスト側の処理がメッセージを「見出し＋クリップの組」へ組み直すため、そのまま流用すると返事の本文が消えるからである。しかしこれは、2つのメッセージが**同じ形**をしていることを見落としていた。どちらも「クリップの組をいくつか持つメッセージ」であり、押下後にやることも「片付いた組を落とす」で同じである。違っていたのは、ダイジェスト側が組み直しのときに**組に属さないブロックを捨てて作り直していた**ことだけだった。

そこで、組み直しを「片付いた組を落とし、**組に属さないブロックはそのまま残す**」に変える。これでダイジェストの見出しも、返信の本文も、触らずに残る。片付けの実装は次の3つに縮む。

- クリップ1件ぶんのブロックに `clip-{n}` の接頭辞を振る（ダイジェストは3ブロック、返信は1ブロック）
- ボタンの `value` からパスを取り、D1を更新する
- そのメッセージが持つ全パスをD1へ問い直し、まだ片付いていない組だけを残して `chat.update` する

**返信側でもD1へ問い直す。** 押された組だけを差し替える実装にしていたが、それでは1通に複数保存された返信で連続してボタンを押したとき、2回目のpayloadに含まれる古い `blocks` が、片付けたばかりの組をボタンごと書き戻す。ADR 0010 がダイジェストについて「例外ではなく通常の経路」と書いた問題は、返信でもそのまま起きる。

### 押した後は、その組がメッセージから消える

ダイジェストの行と同じ挙動にする。返信では、本文はそのままでボタンだけが消える。

当初は「片付けた」の一行へ差し替える案を採ったが、そうすると組み直しがメッセージの種類ごとに割れ、上の統合ができない。**押したものが消えることは、ダイジェストで既に片付けの完了を示す表現として使っている。** 返信だけ別の表現を持つ理由が無い。

トグルは持たせない。取り消しは、スレッドで「戻して」と言えば既存の `set_clip_dismissed` に `false` が渡る。ADR 0010 が決めたとおりで、入口を増やさない。

### ダイジェストの見出しから件数を落とす

見出しは「まだ片付いていないクリップ 7件」だったが、件数を持たせない。

持たせると、ボタンを押すたびに残りを数えて見出しを作り直す必要が生じ、それがメッセージの種類ごとの組み直しを要求する。加えて、投稿時点の件数は通知に出る文（`digestText`）が既に持っており、**見出しの件数はその複製である**。件数が最も役に立つのは通知が届いた瞬間で、そこは変わらない。

### 再送に備えて保存したパスを永続化する

`ThreadAgent` の `handled` テーブルは返信の文面だけを持っていた。Slackへの投稿だけが失敗して再送になったとき、モデルは動かさず記録した返信を投げ直すため、このままでは**その回だけボタンが落ちる**。

`handled_clips(event_id, path, title)` を足し、そのターンで保存できたクリップを返信と一緒に残す。`handled` へ列を足さないのは、既に存在するDurable Objectには `CREATE TABLE IF NOT EXISTS` が効かず `ALTER` が要るためで、表を分ければコンストラクタの既存の書き方のままで済む。

## 検討した代替案

- **返信の文中にマーカーを書かせて拾う**（`[[dismiss:パス]]` のような）: プロンプトを1行足すだけで実装できる。採らない理由は、モデルが書き忘れる／存在しないパスを組み立てるという失敗モードが増えるうえ、既に構造として持っている情報をわざわざ散文に落として読み直す形になるため。ADR 0010 が退けた「ボタン押下を自然文へ落としてAIへ渡す」と同じ筋の悪さがある。
- **「ボタンを出す」ツールをモデルに持たせる**: 判断をモデルに委ねられる。ただしステップが1手増え、「AIがツールを呼ばない」失敗モードが乗るだけで、得られる情報は `save_loaded` の結果と同じである。
- **受付の時点でURLの有無を見て分岐する**: [ADR 0006](0006-agent-with-save-tool.md) の「入力を事前分類しない」に正面から反する。その時点では保存先のパスも、そもそも保存するかどうかも決まっていない。
- **返信用に別の`action_id`と別の押下処理を持つ**: 既存のダイジェスト側を触らずに済む。実際に一度この形で実装したが、パスの取り出し・D1の更新・`chat.update` という**危険な部分がそっくり二重化**し、ハンドラの登録も丸ごと重複した。そのうえ返信側でD1への問い直しを省いたため、連続押下で表示が壊れるバグを作った。既存を触らない代償としては高すぎる。
- **押した後を「片付けた」の一行にする**: 何をしたかがメッセージに残る。ただし組み直しがメッセージの種類ごとに割れ、統合ができない。片付けたことは、押した本人がその場で見ているうえ、ダイジェストでは行が消えることで既に表現している。
- **ボタンを別メッセージとして投稿する**: 返信をブロック形式にせずに済む。ただしスレッドの投稿数が倍になり、どの返信に対応するボタンなのかが読み取りづらくなる。
- **1つの`actions`ブロックにボタンを並べる**: 複数保存したときのブロック数が減る。ただし押されたものだけを落とすのに、ブロックの中身を作り替える必要が出る。1件につき1ブロックなら、そのブロックごと落とすだけで済む。

## 影響

- **Dismissの入口が3つになる。** ダイジェストのボタン、返信のボタン、スレッドの自然文。前の2つは同じ1本の押下処理を通る。
- **ダイジェストの見出しに件数が出なくなる。** 投稿時点の件数は通知に出る文に残る。
- **`chat.update`で通知用の文を作り直さなくなった。** 投稿時のものをそのまま持ち越すため、ダイジェストのメッセージのプレビューに出る件数は、押しても更新されない。本文は正しい。
- **台帳に無いクリップのボタンは、片付いたものと区別せずに消える。** GitHubへの保存は成功したがD1の記録に失敗したクリップがこれにあたる。ADR 0010 が「この不整合を検出する手段は持たない」と書いた状況は変わらない。一度は押下時に区別して伝える実装にしたが、そのために組み直しへ分岐が増えるので採らなかった。
- **同じ記事を同じスレッドで2回送ると、古い返信のボタンが残る。** 上書き保存になるため両方のボタンが同じパスを指す。片方を押すと、もう片方の返信のボタンは押されるまで残る（押せば消える）。
- **返信がブロック形式の投稿になる。** 保存が起きた回だけで、雑談の返信は今までどおりテキストのみ。通知に出る文とブロックを読めないクライアント向けの `text` には、これまでどおり返信全文を入れる。
- **返信本文が3000文字を超えるとsectionに収まらない。** 超える場合は複数のsectionへ分割する。保存直後の返信は60〜120字に収める指示があるが、質問を兼ねたメッセージへの返信は長くなりうる。超えると `invalid_blocks` でメッセージ全体が拒否されるので、投げる前にこちらで割る。
- **Slack Appの設定変更は要らない。** Interactivityの入口は ADR 0014 で `/slack/events` 1本に集約済みで、`action_id` も既存のものを使うため、スコープの追加も再インストールも発生しない。
- **D1のスキーマは変わらない。** 足すのはDurable Object側の表だけで、`schema.sql` の手動適用は不要。
- **`ThreadAgent`の`save`の引数が増える。** 過去に記録された `handled` の行はクリップを持たないため、その再送ではテキストのみが投稿される。
