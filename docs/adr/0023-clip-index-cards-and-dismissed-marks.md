# ADR 0023: 新着一覧をカードと箇条書きに分け、片付けを表示に出す

- ステータス: Superseded（[ADR 0032](0032-clip-page-shows-the-backlog-not-the-newest.md)。`clips/README.md`の自動生成を廃止したため、ここで決めたMarkdownの描画は残っていない）
- 日付: 2026-08-25

## 背景

ADR 0017で`clips/README.md`を派生ビューとして自動生成することを決めた。ただし各行に何を出すかは、日付・タイトル・ホストの3項目という最初の形のまま検討していない。運用してみると2つ困った。

1つは、片付け済みのクリップが一覧で見分けられないこと。ADR 0017は「片付けは表示順と別の注釈」として`dismissed_at`で絞らないと決めたが、絞らないだけでなく印も出していない。片付けたはずのクリップが生きているものと同じ見た目で並ぶため、GitHub上で眺めたときに「片付けが効いていないのではないか」と疑うことになった。

もう1つは、タイトルとホストだけでは記事を思い出せないこと。週次ダイジェスト用にD1へ入れてあるOGP画像と冒頭の抜粋（ADR 0011）を、この一覧は読んでいない。素材はあるのに使っていなかった。

役割で整理すると、週次ダイジェストは「まだ読んでいない」と押してくるもので、`clips/README.md`は自分から見に行って眺める棚である。棚として機能させるには、思い出せる情報と、片付けの状態が要る。

## 決定

- 上位はカード、それ以前は箇条書きにする。合計はADR 0017のまま20件を保つ。
- **カードは片付けていないクリップだけで埋める**（最大5件）。片付け済みは新しくても箇条書きへ落とし、そのぶん後ろから繰り上げる。カードは「これから読むかもしれないもの」の枠と割り切る。20件すべてが片付け済みならカードの節ごと出さない。
- カードには、OGP画像（幅320px）、元記事へリンクしたタイトル、100文字の抜粋、ホストとJSTの`M/D`を出す。読了時間は出さない。本文の文字数を持っておらず、列とバックフィルを足す価値が抜粋と重複するためである。
- カードは**表を使わず、縦に積む**。画像とテキストを横へ並べるにはHTMLの表が要るが、GitHubは表の各セルへ罫線を引くので、カードのつもりのものがマス目に見える。画像を持たない記事（Xの投稿など）では空のセルまで残る。縦に積めば表そのものが要らず、画像の無い記事は行を1つ落とすだけで済む。この描画はGitHubのMarkdown API（`mode: gfm`）で実際に確かめた。単独行の`<img width>`は段落として扱われ、続く行のMarkdownはそのまま解釈される。外部画像はCamoへ書き換えられ、GitHubが`max-width: 100%`を足すため狭い画面でも溢れない。
- **箇条書きは片付け済みに取り消し線**を付ける。リンクは残す。片付けは「読まないと決めた」ことの記録であって、無かったことにするものではない。
- 見出しの下に保存総数とまだ片付けていない件数を出す。一覧は最新20件しか読まないので、棚全体の量はそこからは分からない。
- **抜粋と画像URLはエスケープしてから埋める。** 目的は表示崩れの防止であり、安全ではない。GitHubのサニタイザは`<script>`や`onerror`を落とすが、`<b>`のような無害なタグは素通りさせる。抜粋は記事本文から作るのでHTMLが混じることがある。
- **OGP画像が実際に取得できるかは検証しない。** ダイジェストは`withUsableThumbnails`で事前にGETしているが、あれはSlackが取得できない画像でメッセージ全体を`invalid_blocks`で拒否するための防御である。GitHubはCamo経由で取りに行き、失敗しても壊れた画像1つになるだけでREADMEは壊れない。保存のたびに最大5回の外部リクエストを足す価値はない。
- **片付けたときもREADMEを更新する。** 取り消し線と件数を出す以上、押した結果が反映されないと元の不満がそのまま残る。ボタン押下はlazy handlerで走り30秒使えるので、Slackの3秒ACKには影響しない。Slackのメッセージ差し替えを先に済ませてから更新し、押した手応えを遅らせない。
- **SHAの競合でやり直す回数を1回から3回へ増やす。** Slackで3〜4件を続けて片付けるのは普通の使い方だが、押下ごとに独立した更新が並行するため409が出る。

## 検討した代替案

- **片付け済みを一覧から除外する**: 棚が「これから読むもの」だけになるが、ADR 0017が保存の履歴ビューとして設計した意図を壊す。何をいつクリップしたかを追えなくなる。
- **カードも新着順のまま出し、片付け済みならタイトルに取り消し線を入れる**: 実装は単純だが、読まないと決めた記事に画像付きの大きな面積を割くことになる。
- **HTMLの表で画像とテキストを横へ並べる**: 1件あたりの縦が短く、情報密度は高い。ただしGitHubが各セルへ罫線を引くのでカードが表のマス目になり、画像を持たない記事では空のセルが枠だけ残る。毎日眺める棚として、その見た目を受け入れる価値は無いと判断した。
- **画像をやめて抜粋だけのカードにする**: 最も短く、Markdownとしても素直になる。ただしこの一覧を開く目的は「何を保存したか」を思い出すことで、それを最も助けるのが画像である。縦に伸びるコストを払ってでも残す。
- **読了時間（約何分）を出す**: 記事を選ぶ材料にはなるが、本文の文字数を持つ列とバックフィルの流し直しが要る。抜粋と並べるとカードが情報過多になるため、まず抜粋だけで運用する。
- **Slackと同じく画像を事前検証する**: 壊れた画像を出さずに済むが、保存と片付けのたびに外部リクエストが増える。GitHub側の失敗は局所的で、防ぐ価値に見合わない。
- **片付け時の更新をやめ、次の保存か週次cronに任せる**: 余計なコミットが出ないが、押した直後に反映されない。今回の出発点がまさに「片付けたのに一覧が変わらない」だったので採らない。
- **連打を合流させる（デバウンスやQueueへの積み替え）**: コミットを1つにまとめられるが、そのためにDurable ObjectやQueueメッセージの型を増やすことになる。派生ビューの更新には重い。

## 影響

- 片付けボタンを1回押すごとに、README更新のコミットが1つ増える。4連打すれば「Update clip index」が4つ積まれる。記事の保存ごとにコミットが1つ増えるADR 0017の設計と同じ性質のものとして受け入れる。
- 連打で最後の更新が409のまま落ちると、READMEが1件ぶん古く残る。READMEは毎回D1全体から作り直す冪等な操作なので、次の片付けか保存で正しくなる。
- 20件の中に片付けていないクリップが5件未満しか無ければ、カードもその数になる。
- カードが縦に伸びる。サムネイルを持つ記事が5件続くと、箇条書きへ届くまでスクロールが要る。カードの枚数を減らせば縮むので、長すぎると感じたら`CARD_CLIP_SIZE`で調整する。
- `excerpt`と`image_url`が無い古い行はカードが寂しくなる。バックフィルを流せば埋まる（ADR 0011）。
- 抜粋の書式は再現しない。元記事のHTMLはエスケープされて文字として出る。
