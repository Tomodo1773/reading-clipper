# ADR 0025: スライドは公開されたテキストの範囲でクリップし、取れた範囲を本文に書き残す

- ステータス: Accepted
- 日付: 2026-08-27

## 背景

Speaker Deckとドクセルのスライドを、記事と同じようにクリップしたい。どちらもURLを貼る先として実際に使われている。

しかしスライドは記事と違い、**本文のHTMLを持たない**。中身はPDFから起こした画像で、Markdownへ戻せる構造が無い。このまま一般Web扱いにするとFirecrawlが発表ページをスクレイプするが、そこにあるのは題名と説明文と関連スライドの一覧で、スライドの中身ではない。

両サイトの公開ページを実際に取得して、何が取れるかを確かめた。

**Speaker Deck**は、発表ページに構造化データ（schema.org の `PresentationDigitalDocument`）を埋め込んでいる。そこに題名・著者・公開日・説明文に加えて、**スライド1枚ずつの文字起こし**が `hasPart` として入っている。ページ下部に「Transcript」として人にも見えているものと同じで、`accessibilityFeature: ["transcript"]` と自ら宣言している。ページを1回取れば全文が揃う。

ただしこの文字起こしはPDFから機械的に抜いた文字で、読み順の乱れ、単語の分割（`S Qu BO K`）、図中の文字の混入がある。整形された記事本文とは別物である。

**ドクセル**は、構造化データ（`Article`）に題名・著者・公開日・説明文（「スライド概要」）までしか載せていない。スライドの文字は発表ページのHTMLにも、埋め込みプレイヤーが読むデータにも入っていない（プレイヤーが持つのはページ数とリンクの座標だけ）。PDFのダウンロード経路は robots.txt で拒否されている。**投稿者が書いた概要が上限**である。

もう1つ、保存した後の問題がある。クリップの素性は保存Markdownのフロントマターに入るが、保存済みを読む `read_clip` はフロントマターを読んだ直後に捨てて本文だけを返す。フロントマターに「スライドなので本文はあてにならない」と書いても、このサービス自身のエージェントには届かない。

## 決定

- `speakerdeck` と `docswell` を `ClipSource` に加え、URLの種別判定と専用のフェッチャーを持つ。
- どちらも**発表ページの構造化データを正本にする**。HTMLの見た目からは拾わない。
- 構造化データの読み取りは、それを使うフェッチャーと同じ場所に置く。`html.ts` へは足さない。あのモジュールの存在理由はWorker側とNode側の両方から呼ぶことで、この読み取りを呼ぶのはWorker側だけである。
- **Speaker Deck**: 説明文に続けて、スライド1枚ずつの文字起こしを `## スライド {n}` の見出しで並べる。並び順は配列の順序ではなく `position` に従う。文字起こしは**整形しない**。文字起こしを持たない（画像だけの）発表は説明文だけを残し、`complete` を立てない。
- **ドクセル**: 題名・著者・公開日と説明文だけを保存し、`complete` は**常に立てない**。
- **取れた範囲は本文の末尾に一言で書き残す。** Speaker Deckには文字起こしである旨とその癖を、ドクセルにはスライドの文字が公開されていない旨を書く。
- フロントマターに新しい項目は足さない。機械的な絞り込みは既存の `source_type` で足りる。
- サムネイルは既存の `og:image` 取得（ADR 0011）に任せる。どちらも `og:image` を出している。

## 検討した代替案

- **`fetch_complete` で表す**: 既にある項目で済む。しかしADR 0005 でこの項目は「末尾が省略されている」と定義しており、スライドの事情は別物である。同じ項目に2つの意味を持たせると、読む側はどちらの意味かを判定できない。
- **フロントマターに `body_source` のような項目を足す**: 直接ファイルを開く相手には届くが、`read_clip` がフロントマターを捨てるため、このサービスのエージェントには届かない。届かせるにはツールの返り値の変更（MCP境界にも波及する）が要る。一方、本文へ書けば今日から全経路に届く。読む側に新しい語彙を覚えさせずに済む利点もある。
- **注記を本文の冒頭に置く**: 読み始めてすぐ目に入る。しかしダイジェストと新着一覧の抜粋は本文の冒頭100文字から作る（ADR 0011）ため、**全クリップで抜粋が注記に置き換わる**。採らない。
- **文字起こしの読み順を推測で組み替える**: 読みやすくなる可能性はあるが、直すには元のレイアウト情報が要る。それは公開されていない。推測で並べ替えると、元より読めない本文になり、しかも壊れたことが分からない。
- **ドクセルのPDFを取得して自前で文字を起こす**: robots.txt が明示的に拒否している。投稿者が許可した場合のみの経路でもあり、規約に反する。
- **ドクセルを一般Web（Firecrawl）のままにする**: 実装が要らない。しかし同じページを取って同じ説明文に行き着くうえ、API呼び出しを1回消費し、著者と公開日の精度は落ちる。「スライドである」ことも記録されない。

## 影響

- **Speaker Deckのクリップ本文は、記事より質が低い。** 読み順の乱れ、単語の分割、図中の文字の混入がそのまま残る。AIの要約は元の発表より粗くなる。末尾の一言はそれを伝えるが、防ぐわけではない。
- **ドクセルのクリップにはスライドの中身が無い。** 検索（`find_clips` はGitHubのコード検索）はスライド本文に当たらないため、概要に無い語では見つからない。要約も概要ベースになる。
- 保存Markdownの本文に、取得側が書いた1行が混ざる。ADR 0005 の「フロントマターの直下は取得した本文そのまま」を、この範囲で上書きする。ADR 0005 が禁じたのは見出し・元URLのリンク・セクションという**構造**で、取得の事情を書き残すこと自体は、本文が上限を超えたときの省略の注記として既に行っている。
- **説明文が極端に短いドクセルのクリップでは、ダイジェストの抜粋に末尾の注記が混じる。** 抜粋は本文の冒頭100文字から作るため、説明文がそれに満たないと注記まで届く。その場合、他に見せる材料も無い。
- Speaker Deckの発表ページと同じ `/{1}/{2}` の形をした自身のページ（カテゴリ、特集、機能紹介、埋め込みプレイヤー）は、先頭要素の除外リストで落とす。Speaker Deckが新しい予約パスを増やすと、それが発表ページとして扱われる。
- 文字起こしが1本も無いSpeaker Deckの発表は、ドクセルと同じ「概要だけ」の状態になる。本文からはどちらのサイトかが分からないが、フロントマターの `source_type` に残る。
