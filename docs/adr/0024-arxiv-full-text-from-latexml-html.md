# ADR 0024: arXivの論文はLaTeXML版HTMLから全文を取得する

- ステータス: Accepted
- 日付: 2026-08-27

## 背景

`arxiv.org/abs/{id}` は種別判定で「その他のWebページ」に落ち、Firecrawlで取得していた。しかしabsページは論文の入口であって、タイトル・著者・アブストラクト・各形式へのリンクしか含まない。**本文が1文字も無いページを取りに行っていた**ため、保存されるのはアブストラクトだけだった。

arXivが本文をどの形で配っているかを実際のHTTPレスポンスで確認した。

| 試したURL | 結果 |
|---|---|
| `https://arxiv.org/abs/{id}` | 200。約44KB。アブストラクトのみで本文を含まない |
| `https://arxiv.org/html/{id}` | 200。約191KB。**LaTeXMLが生成した全文HTML** |
| `https://arxiv.org/pdf/{id}` | 200。全文だがPDFのパースが要る |
| `https://arxiv.org/src/{id}` （TeXソース） | robots.txtで`Disallow` |
| `https://export.arxiv.org/api/query?id_list={id}` | 200。約3.7KB。アブストラクトのみ |
| `https://ar5iv.labs.arxiv.org/html/{id}` | absへリダイレクトして戻る。この論文は未生成 |

robots.txtは`/html`を明示的に`Allow`し、`/src`と`/api`を`Disallow`している。TeXソースから組み立てる案は、この時点で方針として取らない。

`/html/`はバックフィルが進んでおり、新しい論文だけでなく2017年の`1706.03762`や2002年の`math/0211159`も200を返す。2007年から2026年まで8本を当たった範囲では、全部にHTML版があった。

LaTeXMLの出力は機械生成で、意味づけの残る安定した構造を持つ。見出しは`<h1>`〜`<h6>`、段落は`<p class="ltx_p">`、数式は`<math>`要素で、LaTeX原文が`alttext`属性に入っている。ADR 0003でZennの`body_html`に対して行った判断と、対象の性質が同じである。

## 決定

arXivの論文（`arxiv.org` の `/abs/`、`/html/`、`/pdf/` いずれか）を専用の種別として扱い、LaTeXML版HTMLから本文をMarkdownへ変換する。

### 取得はabsページを起点にする

1. `https://arxiv.org/abs/{id}` を取得し、タイトル・著者・公開日を`citation_title` / `citation_author` / `citation_date`のmetaから取る。同時に、全文HTMLへのリンク`<a id="latexml-download-link">`の有無を見る。
2. リンクがあれば、そこに書かれた**版まで確定したURL**（`/html/{id}v{n}`）を取得して本文を変換する。取得した版はこのURLから決まる。
3. リンクが無ければ、absページのアブストラクトだけを保存し、`fetch_complete`をfalseにする。汎用のFirecrawl経路へはフォールバックしない。

`/html/{id}`を直接叩いて404で在庫を判定する方式を採らないのは、absページのリンクがarXiv自身による在庫の宣言であり、かつ2回のリクエストの間に改版が入っても版を取り違えないためである。著者を全文HTML側から取らないのは、そこには所属とメールアドレスが混ざるのに対し、absページのmetaは名前だけが並ぶためである。

### 変換器を共有部品として切り出す

ADR 0003でZennのために書いたHTML→Markdown変換器を`src/html-markdown.ts`へ切り出し、2つ目の利用者としてarXivが使う。依存パッケージは追加しない。

切り出しにあたって、**共有部品とサイト固有ルールを分ける**。従来はZenn固有の分岐（`embed-katex`、`aside`の`msg-content`、`div.code-block-container`）が共有部分の`switch`へ直接書かれていた。arXiv固有の分岐を同じ場所へ足すと、1つの部品の中に2サイトぶんの固有ルールがサイト名ごと並ぶ。2つ目の利用者が現れて境界が見えたので、ここで分ける。

- 変換器は「インライン用」「ブロック用」の関数を1つずつ受け取る。ルールは自分で組み立てた結果を返すか、`undefined`を返して共通処理に任せるかを選ぶ。プラグイン機構は作らない。
- 相対URLの解決は共有部品側に置く。HTMLの相対URLを文書のURLで解決するのはHTMLの一般的な意味であり、サイト固有の話ではない。arXivの図は`src`が相対パスで来るが、Zennの`body_html`は絶対URLなので結果は変わらない。

### arXiv固有ルールは3つ

| 対象 | 変換 | 理由 |
|---|---|---|
| `<math alttext="...">` | `$...$`、`display="block"`なら`$$...$$` | 共通処理へ落とすとMathMLの中身とTeX注釈が二重に出る |
| `div.ltx_listing` | 行ごとの`div.ltx_listingline`をコードブロックへ組み直す | `<pre>`ではないため、放置すると擬似コードが1行ずつ段落へ割れる |
| `div.ltx_authors` と `span.ltx_pubnotes` | 落とす | タイトルと抄録の間に並ぶ書誌の飾り。著者名はフロントマターへ`citation_author`から入り、本文側の同じ並びは所属とメールアドレスが混ざって1,500字ほどになる。CCS分類も100字ほど抄録の手前に居座る。落とさないとダイジェストの抜粋（ADR 0011）が抄録へ届かず、どの論文も連絡先と分類語で埋まる |

本文の選別は木の構造で行い、`article.ltx_document`だけを変換する。左のTOCサイドバーには本文と同一の文字列が並ぶため（「Reasoning-Aligned Rubric Tuning」が目次に1か所、本文に7か所）、テキストでは選別できない。ページ末尾の資金提供者ロゴも同時に外れる。

図には固有ルールを置かない。相対URLさえ解決すれば共通の`img`処理が`![alt](url)`を出し、LaTeXMLが`alt`に書いた説明とともにGitHub上で図が見える。章内の相互参照（`<a href="#...">`）も、共通処理がアンカーリンクをテキストだけにするため追加処理は要らない。

**参考文献は落とさず残す。** 実測で本文45,799文字（うち参考文献6,774文字）、変換後のMarkdownで48,444文字であり、保存上限200,000文字にも`read_clip`の読み戻し上限60,000文字にも収まる。

### canonical URL

`https://arxiv.org/abs/{id}`（バージョンなし）に正規化する。

これはarXiv自身の宣言に従う。`/abs/{id}v1` のページが `<link rel="canonical" href="https://arxiv.org/abs/{id}">` を出しており、バージョンは別資源ではなく同一資源の版だという立場を取っている。`abs`が論文の識別で、`html`と`pdf`はその表現である。同じページの`og:url`は版を含んでおりarXiv内で食い違うが、識別を宣言しているのは`canonical`の側である。

- `www.arxiv.org`は`arxiv.org`へ寄せる。既存のQiita・Zennの正規化と同じ形。
- IDは新形式（`2608.18300`）と旧形式（`hep-th/9108001`、`math.AG/0611234`）の両方を受ける。旧形式はパスにスラッシュを含む。
- 取得した版は保存するMarkdownのフロントマターに`source_version`として残す。

## 検討した代替案

- **Firecrawlに渡すURLを`/abs/`から`/html/`へ書き換えるだけにする**: 変更は最小で済むが、左のTOCサイドバーとUIを`onlyMainContent`がどう扱うかは検証できておらず、数式の`alttext`は汎用の抽出では拾われない。既に手元に変換器がある以上、外部サービスの往復とコストを足す理由がない。
- **`HTMLRewriter`で流し読みしながら変換する**: 依存を足さずに済むが、要素が開始・テキスト・終了の順に細切れで届くため、本文の繋ぎ直しと「今どの領域にいるか」の管理を自前で持つことになる。既存の変換器は木に組んでから変換しており、同じことを別の方式で二度書く形になる。左のTOCの除去も、木なら「本文のかたまりを選ぶ」だけで済む。
- **`turndown`のような汎用ライブラリを追加する**: ADR 0003と同じ理由で採用しない。DOM実装を伴う依存がバンドルへ乗る。加えて、TOCの除去・`alttext`の取り出し・listingの組み直しというarXiv固有の判断は、どの汎用変換器を使っても外側に残る。汎用部分は既に手元にある。
- **共有部品にarXiv固有の分岐を足す（切り出さない）**: 変更は小さいが、Zenn固有の分岐と混ざったまま増える。3サイト目で破綻する形を先送りするだけになる。
- **PDFを解析する**: robots.txt上は許されているが、2段組と数式の復元が要る。HTMLが同じ内容を構造付きで配っている以上、選ぶ理由がない。
- **TeXソースから組み立てる**: robots.txtが`/src`を`Disallow`している。
- **arXiv APIを使う**: アブストラクトしか返さず、今の問題を解決しない。
- **canonicalにバージョンを含める**: 改版ごとに別のクリップとして残せるが、arXiv自身のcanonical宣言に反する。同じ論文が版ごとに別件として一覧へ並ぶことになる。

## 影響

- LaTeXMLの出力構造が変わると、変換結果の見た目が変わりうる。`article.ltx_document`が見つからない場合は失敗として扱うため、arXivの論文だけがクリップに失敗し、Slackへ通知されてdead letter queueへ送られる。壊れたまま中途半端な本文を保存しない。
- HTMLが未生成の論文では、保存されるのがアブストラクトだけになる。`fetch_complete`がfalseになり、本文が省略されている事実がAIの応答にも出る。この経路は実在の論文で試せていない。当たった8本すべてにHTML版があり、反例を見つけられなかったため、確認は単体テストの合成データに頼っている。
- 参考文献を含めるため、1件あたりの保存量が他のクリップより大きい。極端に参考文献の長い論文では読み戻しが60,000文字で切れうる。
- 数式は`$...$`のまま保存する。GitHub上のMarkdownでは数式として描画されるが、Slackの返信では記法がそのまま見える。擬似コードのコードブロック内では、数式は記法のまま残る。
- 著者の所属とACMのCCS分類は保存されない。著者はフロントマターに`citation_author`の名前だけが残り、分類は元ページで見ることになる。
- ダイジェストのサムネイルは、absページの`og:image`が論文ごとの画像ではなく共通のarXivロゴであるため、arXivのクリップはすべて同じロゴになる。
- `loadContent`経由では、`fetchPageHead`の部分GETと合わせてリクエストが3本になる。2本にするには`fetchPageHead`の結果をフェッチャーへ渡す必要があるが、フェッチャーは`fetchPageHead`を通らない`fetchContent`経由でも動く必要がある。「フェッチャーが自分で必要なものを取る」という既存の構造を崩さず、3本を受け入れる。
- 変換器の切り出しにより、Zennの取得経路も新しい共有部品を通る。等価であることは、既存のZennのテストを変えずに通すことで確認している。
