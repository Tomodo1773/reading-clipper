# ADR 0037: `list_clips`は該当が多くても、新しい順の上位と総数を返す

- ステータス: Accepted
- 日付: 2026-11-20

## 背景

[ADR 0031](0031-list-clips-from-the-file-tree.md)は、`list_clips`の該当が100件を超えたら項目を返さず、`matched`と`too_many`だけを返すと決めた。任意の一部を返すと、利用者にもモデルにも「それが全部だ」と誤らせるからである。同じADRは、題名の語を渡さない全件列挙が成り立つのは保存数が100件に届くまでの約3週間で、それ以降は劣化ではなく正しい挙動だと書いた。

その見積もりどおりに100件を超えた。超えてから困ったのは、「最近クリップした記事」「まだ片付けていない記事」が取れないことである。どちらも題名の語では絞れない。語を足して絞るよう求められても、出す語がない。手段として残っていたのは本文検索の`find_clips`だけで、こちらは最大5件しか返さず、順序も新しさではない。

ADR 0031が避けたかったのは、**どこで切ったか分からない一部**である。新しい順という決まった順序で上位N件を返し、総数を添えれば、返した項目が全体のどこに当たるかは形から読める。

## 決定

### 2つの引数を足す

- `limit`: 返す件数。1〜100。省略すると上限の100。
- `dismissed`: `false`なら片付けていないものだけ、`true`なら片付けたものだけ。省略すると両方。`set_clip_dismissed`の引数と同じ名前・同じ意味にそろえる。

### 該当が多くても、空では返さない

題名の語と`dismissed`で絞った該当数を`matched`として返し、新しい順で上位`limit`件を`found`に入れる。`too_many`は廃止する。

`matched`の意味は変えない。全件を走査したときにだけ返し、`matched === 0`は保存されていないという事実として使える。`found`の件数が`matched`より少ないことが、続きがあることの印になる。

上限の100件は残す。1回のツール応答に収める量の見積もりで、[ADR 0031](0031-list-clips-from-the-file-tree.md)の理由がそのまま当てはまる。省略時もこの上限まで返す。引数を省いた呼び出しは、100件以下の蔵書では今までどおり全件を返し、それを超えると直近100件になる。少なく欲しいときはモデルが`limit`を渡す。

### 台帳は全行を1回で読む

並べ替えと`dismissed`での絞り込みには、該当した全件の`clipped_at`と`dismissed_at`が要る。今までの`selectClipsByPath`はパスを`IN (...)`へ並べる。D1のクエリは束縛できる値が100個までなので、100件を超える該当には使えない。

そこで一覧は、閲覧ページと同じ`selectAllClips`で台帳を1回だけ読み、手元でパスを突き合わせる。行数がクリップ数に比例するのは閲覧ページと同じで、[ADR 0032](0032-clip-page-shows-the-backlog-not-the-newest.md)の見積もりの範囲に収まる。母集団は今までどおりGitHubのファイル一覧で、台帳は注釈のままである。

### 台帳が読めないときは、順序を名乗らない

今までは台帳が読めなくても、注釈なしで項目を返していた。100件以下を全部返すかぎり、順序が崩れても嘘にはならなかった。上位N件を返すようになると、順序が分からないまま返せば「新しい順の上位」を名乗る嘘になる。

- `dismissed`を渡された場合、または該当が`limit`を超える場合は、台帳が読めなければ`failed_at`を返して失敗にする。
- それ以外（該当を全部返せる場合）は、今までどおり注釈なしでパス順に返す。題名での在否確認は台帳の障害に影響されない。

### 台帳に行が無いクリップは、片付けていないものとして扱う

片付けの印は台帳の行にしか付けられない（`set_clip_dismissed`は行が無ければ`updated: false`を返す）。行が無いクリップは、一度も片付けられていない。`dismissed: false`には含め、`dismissed: true`からは外す。新しい順では、今までどおり末尾に来る。

返す項目の`dismissed`は`null`のままにする。この値は「台帳の注釈が無い」ことを表していて、絞り込みでの扱いとは別の情報である。

## 検討した代替案

- **期間（いつからいつまでに保存したか）で絞る**: 「先週の記事」に直接答えられる。採らない理由は、新しい順の上位に`clipped_at`が付いていれば、モデルがそこから判断できるため。必要になってから足す。
- **古い順で並べる**: 放置している記事を探せる。採らない理由は、閲覧ページがすでに片付けていないものを全件見せており（[ADR 0032](0032-clip-page-shows-the-backlog-not-the-newest.md)）、積読を見直す面はそちらが担うため。
- **ページ送りを持つ**: [ADR 0031](0031-list-clips-from-the-file-tree.md)と同じ理由で採らない。続きが要るときは、語を足すか`limit`を上げる。
- **省略時の件数を上限より小さく（20件など）する**: 「最近の記事」への応答が軽くなる。採らない理由は、100件以下の蔵書で引数を省いたときに全件が返らなくなり、上限と既定値という2つの値を持つことになるため。件数を絞りたい場面ではモデルが`limit`を渡せる。
- **`too_many`を残し、`limit`を渡したときだけ上位を返す**: 既存の形を壊さない。採らない理由は、引数を省いた呼び出しが100件を超えた蔵書では必ず空になり、その状態が既定の挙動として残るため。
- **`selectClipsByPath`を100件ずつに分けて引く**: 既存の関数を使い回せる。採らない理由は、該当の数だけ往復が増え、全行を1回で読む閲覧ページと同じ規模の読み出しを、より手間のかかる形でやることになるため。

## 影響

- 「最近クリップした記事」「片付けていない記事」が、蔵書の大きさによらず取れる。
- 引数を省いた`list_clips()`は、100件を超える蔵書でも新しい順の100件と総数を返す。`too_many`を前提にした呼び出し側は無い（BotとMCPはどちらもモデル経由で、契約は説明文で伝わる）。
- 台帳が落ちているあいだは、件数で切る一覧と`dismissed`での絞り込みが失敗する。題名で全件を返せる在否確認は動く。
- 一覧のたびに台帳を全行読む。行には抜粋も含まれるが、数百件で数百KBに収まる。
