# ADR 0004: Slackへ返す要約は1〜2文の簡潔な一言にする

- ステータス: Accepted
- 日付: 2026-08-16

## 背景

READMEの初期方針では、要約を2〜4文とし、Geminiには「テーマと結論を1文、主要な内容を1文」で返させることにしていた。

実際の記事で試すと、この2文固定が問題になった。1文目でテーマと結論を書き切ってしまう記事が多く、2文目は「具体例やコード例も紹介されている」のような、どの記事にも当てはまる無価値な文になりやすい。長さを埋めるために内容の薄い文を足させる形になっており、読むかどうかの判断材料が増えていなかった。

要約はSlackのDMで、通知欄やスレッドの1行として読まれる。文の数を保証することよりも、その記事固有の中身を短く伝えることの方が用途に合う。

## 決定

- 要約は日本語で1〜2文、全体で60〜120字程度の簡潔な一言にする。文の数は固定しない。
- 伝えるのは「何についての記事か」と「要するにどういうことか（結論・肝）」の2点に絞る。結論に至る主要な内容は、要約の必須項目から外す。
- `SummaryResult` は `{ sentences: [string, string] }` をやめ、`{ text: string }` にする。文の分割はアプリで扱わない。
- 取得の不完全性とGitHubの保存結果は、これまでどおりアプリ側で文を足して伝える。
- 要約とSlackへの返信の口調は、面倒見のいい年上のお姉さんのタメ口に統一する。要約とアプリ側の固定文が地続きに読めるようにするため。

## 検討した代替案

- **2〜4文のまま、2文目の指示を「具体があるときだけ書く」に緩める**: 文の数を型で保証したままにできるが、モデルは指示された構造を埋めようとするため、薄い2文目が残りやすい。型で長さを縛る意味も薄い。
- **要約を箇条書きにする**: 情報を詰められるが、Slackの1行プレビューで読めなくなる。「読むかどうかをその場で判断する」という用途から外れる。
- **口調を指定しない**: 無難だが、毎回同じ言い回しの機械的な要約になりやすい。温度を上げても定型に寄る傾向があったため、キャラクターを与えて切り口を変えさせる方を採った。

## 影響

- 記事の内容の網羅性は落ちる。結論に至る根拠や手順は要約からこぼれるため、詳細は保存したMarkdownを読む前提になる。
- 出力が自由長になるため、極端に長い要約が返る可能性がある。長さはプロンプトだけで抑えており、アプリ側で切り詰めていない。
- 口調を指定した分、事実の要約としては表現の揺れが増える。温度も0.8と高めに設定している。事実を曲げないことはプロンプトの「入力された本文だけを根拠にする」で担保する。
- 要約の文の数に依存した表示や後処理は将来も持てない。`SummaryResult` は1つのテキストとして扱う。
