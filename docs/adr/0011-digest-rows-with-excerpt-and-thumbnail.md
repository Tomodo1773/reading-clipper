# ADR 0011: 週次ダイジェストの1件を、抜粋とサムネイル付きの3ブロックで表す

- ステータス: Accepted
- 日付: 2026-08-17

## 背景

[ADR 0010](0010-weekly-digest-and-dismiss-bit.md) で作った週次ダイジェストは、1件を「タイトルのリンク1行＋片付けるボタン」で表していた。実際に運用してみると、タイトルだけでは記事の中身を思い出せず、片付けるかどうかをその場で判断できない。

本番D1の中身を確認したところ、表示が壊れている原因は表示側のコードではなく台帳の中身だった。

- **未片付けの全行で `url` が `NULL`。** `clipHref` はGitHubのファイルへフォールバックするため、ダイジェストのリンクが全部GitHubを指していた。ADR 0010 が「バックフィルは `url` にNULLを入れ、フロントマターは読まない」と決めたことの直接の帰結である。
- **`clipped_at` も全行が同じ値**（バックフィルの実行時刻）で、本物の保存日時はフロントマターにしかない。
- **タイトルがパス由来で劣化している。** ADR 0005 でファイル名を記事タイトルそのものにしたが、長い題名は `makeClipFileName` が削るため、`全体像` や `i-web-status-2088190316381872181-89f74929f0e2f45a` のような表示になる。正しい題名はフロントマターの `title` にある。

つまり、表示に必要な値はすべてGitHub側に揃っていて、D1へ複製されていないだけだった。

og:image についても実測で確認した。フェッチャーが叩いているAPI（Zennの非公式API・Qiitaの `.md`・X API）はどれも画像を返さないが、**記事ページのHTMLを見れば Qiita・Zenn・X・一般Webのすべてで `og:image` が取れる**。

一方、Slackの制約も確認した。**`image_url` はSlackがサーバー側で取得しにいき、取れなければ `invalid_blocks`（`downloading image failed`）でメッセージ全体を拒否する。** 画像だけ表示されない、という挙動ではない。`section` の `accessory` は要素を1つしか置けないため、サムネイルを置くと「片付ける」ボタンの居場所が無くなる。

## 決定

### 表示

- 1件を **section（タイトルのリンクと抜粋、`accessory` にサムネイル）+ actions（片付けるボタン）+ context（ホスト名・保存時期）の3ブロック**で表す。7件で `1 + 1 + 7×3 = 23` ブロックとなり、Slackの上限50に収まる。ADR 0010 の「7件×（セクション＋ボタン）」という記述はこれで置き換える。
- 抜粋は本文の先頭100文字。Markdownの記法を剥がして1行に潰す。
- 各項目のあいだに `divider` を入れない。7本ぶん縦が伸びるだけで、区切りは `context` の小さなメタ行が担う。
- **`og:image` を `image` ブロックで全幅表示しない。** 1件あたり250px以上を占め、7件で1000pxを超える。QiitaとZennの `og:image` は記事タイトルを描いた自動生成カードで、隣に出ているタイトルの二度書きにあたるため、大きく出す価値がそもそも小さい。

### データの出どころ

D1に `title` / `excerpt` / `image_url` の3列を足し、**保存時に複製する**。

| 表示要素 | 出どころ | 取れないとき |
|---|---|---|
| タイトル・本体URL・抜粋・保存時期 | D1（保存時に複製） | 発生しない |
| サムネイル | D1（保存時に取得した `og:image`）＋投稿前に到達性を検証 | その行だけ画像なし |

- **テキストは外部fetchに依存させない。** 記事サイトが落ちていても失うのはサムネイルだけで、ダイジェストは必ず投稿される。
- `og:image` はソースで分岐せず、記事ページのHTMLから一律に取る（`fetchOgImage`）。Firecrawlのmetadataから拾う経路を別に作ると、同じ値の出どころが2本に割れる。取得は本文の取得と並列に走らせ、**失敗はすべて `undefined` にして投げない**。サムネイルの不在がクリップの保存を巻き添えにしてはならない。
- `image_url` は **フロントマターにも書く**。ADR 0010 の「D1が失われても母集団はGitHubから再構成できる」を保つため、D1にしか存在しない値を作らない。
- `recordClip` の `ON CONFLICT` は新しい3列も更新する。ここに足し忘れると、記事が更新されても古い表示が出続ける。`clipped_at` は最初の保存時のままにする（保存し直しは新しいクリップではない）。

### サムネイルの検証

**投稿前に `image_url` をGETして、ステータス200かつ `content-type` が `png` / `jpeg` / `gif` のものだけを採用する。** 3000文字（Slackの `image_url` 上限。Qiitaの自動生成OGPには2651文字の実例がある）を超えるURLも捨てる。

- 投げてから `invalid_blocks` を受けて画像なしで投げ直す案は採らない。Slackはメッセージ全体を拒否するため、**死んでいる画像が1件でも7件ぶんの画像が消える**。事前に検証すれば、その1件だけ画像なしにして残りは保たれる。加えて、年に1回動くかどうかの投げ直し分岐は、いざ動くときには壊れている。
- HEADではなくGETで確かめる。HEADを拒否してGETだけ通すCDNがあり、Slackが実際に行うのはGETだからである。本文は読まずに打ち切る。
- **検証は完全ではない。** 検証するのはWorkersで、実際に取得するのはSlackなので、User-Agentやアクセス元による振り分けで結果が食い違いうる。これはリスクをゼロにするものではなく減らすものである。
- それでも投稿が落ちた週は、`markDigestShown` が投稿成功後にしか走らない（ADR 0010）ため、**同じ7件が翌週そのまま出てくる**。失うのは1週ぶんの通知だけで、順番の後ろへ回ることもクリップが失われることもない。この自己回復があるので、投げ直しの分岐を持たない判断が成り立つ。
- この検証は**絶対に例外を投げない**。`scheduled` は例外をそのまま再throwするため、ここで投げるとダイジェストごと落ちる。

### Dismissの差し替え

- **payloadの `blocks` を再利用する方針（ADR 0010）は維持する。** D1から作り直すと、ボタンを1回押すたびに残り全件のサムネイルを取り直すことになる。ADR 0010 は単純さを理由にこの方針を採ったが、いまはより強い理由が付いた。
- 1件が複数ブロックに散るため、**`block_id` の接頭辞（`clip-{連番}`）で組をまとめる。** パスをそのまま `block_id` に入れない。ファイル名が記事タイトルそのままなので、`block_id` の255文字上限を超えうる。パスは従来どおりボタンの `value` から取る。

### ダイジェストは冪等キーを持たない

`postSlackMessage` の `idempotencyKey` を任意にし、**ダイジェストからは渡さない。**

このキーは `client_msg_id` に決定的UUIDを詰めるもので、Slackは同じ値の投稿を重複と見なし、新しいメッセージを作らずに既存の `ts` を返す。ダイジェストは当初 `digest:{日付}` を渡していたが、これは要件があって付けたものではなく、`postSlackMessage` の必須パラメータを埋めるために日付を入れただけだった。必須である理由はQueue経路にある。

- **重複排除が要るのはQueue経路だけである。** Cloudflare Queuesは at-least-once で、`message.ack()` の前に落ちれば同じジョブが再配送され、同じ返信が2通出る。`${job.jobId}:reply` と `${job.jobId}:failure` はこれを防いでいる。ここは維持する。
- **cronは再試行されない。** ハンドラが例外を投げてもCPU時間を超えても、次の発火まで再実行されない。ダイジェストには排除すべき重複が存在しない。
- **渡すと逆に壊れる。** 重複と見なされたときもSlackは `ok` と既存の `ts` を返すため、`postSlackMessage` は投稿できたものとして返る。呼び出し側はこの2つを区別できない。同じ日に2回走ると、`runWeeklyDigest` は**一度も表示されていないクリップに `markDigestShown` を打つ**。ADR 0010 が「印を打つのはSlackへ投稿できてから」と決めた保証が、このキーによって成立していなかった。
- **重複して届いても壊れない。** `setClipDismissed` は冪等で、`keepClipBlocks` は残す行をD1へ問い直すため、古いほうのメッセージのボタンを押しても正しく縮む。**見える失敗（2通届く）と、見えない破損（クリップが表示されないまま提示済みになる）なら、前者を選ぶ。**

副次的な利点として、手動でcronハンドラを叩いたときに実際に投稿されるようになり、レイアウトの変更を実物で確認できる。従来は同じ日に叩くと既存メッセージのtsが返るだけで、何も起きなかった。

### バックフィル

**`git clone --depth 1` したディレクトリを引数で受け、フロントマターを読む。** ADR 0010 は「フロントマターの読み出しはO(N)リクエストになる」としてこれを避けたが、cloneすればGitHubへのリクエストは1回で済む。そもそもO(N)を避ける制約は再試行の無いcronの経路についてのもので、手元で1回だけ走らせる復旧スクリプトには当てはまらない。

- `source_url` / `title` / `clipped_at` / `image_url` を読み、本文から抜粋を作る。`image_url` が無い記事は `og:image` を取りに行く。ここだけは記事数ぶんの外部リクエストが出るが、手動実行のスクリプトなので許容する。
- UPSERTは**GitHubから導ける列（`url` / `title` / `excerpt` / `image_url` / `clipped_at`）をすべて上書きし、導けない `last_shown_at` と `dismissed_at` だけを残す。** D1はGitHubに対する注釈レイヤーなので、これが「作り直す」の正しい意味になる。既存の値を温存する（`COALESCE`）と、旧版のバックフィルが入れた嘘の `clipped_at` も、抜粋の規則を変える前の値も修復できず、復旧スクリプトが復旧に使えなくなる。
- 本文が別のフロントマターで始まるクリップ（Qiitaは原稿ごと保存されている）と、旧世代のキー（`slack_event_id` / `summary_status`）が混在する。パーサは最初のブロックだけを読み、未知のキーは無視する。
- 抜粋の作り方は保存時とバックフィルで一致していなければならない。そのため `clipExcerpt` を、何もimportしない `src/excerpt.ts` に置いて両方から共有する。Workers用とNode用でtsconfigが分かれているので、依存を持たせるとスクリプト側から使えなくなる。

## 検討した代替案

- **`og:image` を毎週ダイジェスト生成時に取得する**: 常に新鮮な画像が使え、D1に列が増えない。採らない理由は、再試行の無いcronの上で毎週7本の記事ページ取得（HTMLのパースを含む）を抱えることになり、ADR 0010 が意図的に選んだ「D1のクエリ1本とSlack API 1回」という形を崩すため。Dismiss時はpayloadから画像URLを引き継ぐので、同じ値の出どころが2系統に割れる点も悪い。なおimgix（Qiita）とcloudinary（Zenn）の署名はパスのHMACであって期限付きトークンではないため、保存した値が陳腐化するリスクは低い。
- **投げてから失敗したら画像なしで投げ直す**: 検証のためのGETが要らない。採らない理由は本文に書いたとおりで、失敗の粒度がメッセージ全体になることと、ほぼ実行されない分岐が増えること。
- **サムネイルを `context` ブロックの画像要素にする**: 20pxなので縦が伸びず、ボタンを `accessory` に残せる。ただしその大きさでは記事の見分けが付かず、出す意味がない。
- **先頭1件だけ `image` ブロックで大きく出す**: 見た目に強弱が付く。採らない理由は、先頭を特別扱いする意味付けが無いこと（並び順の1位でしかない）と、画像取得の可否でレイアウトが揺れること。
- **一覧の見出しを `section` のままにする**: 既存コードのままで済む。`header` ブロックにすると太く大きく出て、一覧の頭であることが一目で分かるので変更した。0件のときだけは `header` に本文を入れられないため、`header` + `section` の2ブロックにする。
- **`title` を列に持たず、毎回GitHubから読む**: 列が増えない。ダイジェスト生成時にO(N)のGETが要るので採らない。
- **Slackの自動unfurlに任せる**: URLを貼るだけで記事のプレビューが出る。採らない理由は、unfurlの結果がblocksの後ろにattachmentsとしてまとめて出るため、各行の「片付ける」ボタンとプレビューが切り離されること。どのリンクを展開するかも大きさも制御できず、1メッセージあたりの展開数にも上限がある。なおこのBotは `unfurl_links` / `unfurl_media` をいずれも `false` にしている。

## 影響

- **D1の列が5つから8つに増える。** `schema.sql` は `CREATE TABLE IF NOT EXISTS` の1文だけで構成する制約があるため（テストが全体を1文として流す）、既存DBへは `ALTER TABLE` を手で3本流す必要がある。手順は `schema.sql` のコメントとREADMEに書く。
- **保存時の外部リクエストが1本増える。** 本文の取得と並列に走らせるため待ち時間は増えないが、記事サイトへのアクセスが1回増える。
- **ダイジェスト生成時に最大7本のGETが増える。** サムネイルの検証ぶんで、いずれも失敗してもダイジェストは投稿される。
- **バックフィルにネットワークアクセスが増える。** 復旧の所要時間がクリップ数に比例するようになった。GitHubへのリクエストは1回のままである。
- **`og:image` が無い記事、取れなかった記事は画像なしで出る。** 行の高さが揃わないが、テキスト側は必ず揃うため一覧としては読める。
- **旧世代のクリップは表示が完全には直らない。** フロントマターの `title` 自体が誤っているファイル（保存当時のフェッチャーの不具合による）は、バックフィルしても誤ったままになる。同じURLを保存し直せば `title` / `excerpt` / `image_url` が更新されるので、直したいものは個別に再クリップする。
- **`clipExcerpt` の変更は過去の抜粋へ遡及しない。** 保存済みの行はバックフィルを流し直さない限り古い規則のままである。
- **Slackが画像の取得に失敗した週は、ダイジェストが投稿されない。** 検証を通り抜けたものだけが残るリスクで、その週の通知は失われる。翌週に同じ7件が出るため回復はするが、失敗したこと自体は利用者に見えない。
