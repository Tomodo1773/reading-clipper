# ADR 0015: GitHubから消えたクリップは、ダイジェストに出す直前に実在を確かめて落とす

- ステータス: Accepted
- 日付: 2026-08-20

## 背景

[ADR 0010](0010-weekly-digest-and-dismiss-bit.md) は、GitHubから手でファイルを消したときにD1へ残る孤児行について、突き合わせを行わないと決めた。理由は2つだった。

1. 孤児行はダイジェストに1度出たあと「片付ける」を1回押せば二度と出てこないので、実害が1回の表示に収まる。
2. ダイジェスト生成時にTrees APIと突き合わせると、cronの経路にGitHub App認証と一覧取得が丸ごと増え、ダイジェストがGitHubの障害で落ちるようになる。

1つ目が成り立たない。

- 実害が1回で収まるのは、利用者がその行をゴーストだと気づいて片付けを押した場合だけである。押さなければ `last_shown_at` が更新されて順番の後ろへ回るだけで、プールからは消えない。在庫が一巡すればまた出る。
- そもそもゴーストかどうかを見分ける手段が無い。ダイジェストのリンク先は記事のcanonical URLなので、開けば記事が普通に読める。GitHubから消えていることは画面のどこにも現れない。
- GitHub上でファイルを消す操作は、片付けボタンより強い意思表示である。ボタンは注釈を1つ立てるだけだが、削除は正本そのものを捨てている。それを週次で出し直して再度の意思表示を要求することは、ADR 0010 自身が最大のリスクとして挙げた「通知が無視され始める」を、こちらから招く。

2つ目は、突き合わせを必須処理にしない限り成立しない。

## 決定

- **ダイジェストに出す直前に、これから出す行だけGitHub上の実在を確かめる。** 台帳全体をGitHubと同期する処理は作らない。
- 手順は次のとおり。
  1. 台帳から候補を出す件数より多めに取る（`DIGEST_CANDIDATES` = 10）。
  2. 候補それぞれについて、Contents APIでファイルを引く。保存時に使っているものと同じ経路を使う。
  3. **404が返ったものだけ**、台帳から行を消して候補から外す。
  4. 残りの先頭7件を投稿する。
- **削除は404を見たときだけ行う。** 認証の失敗、タイムアウト、5xx、その他の例外はすべて「不明」として扱い、行は残して候補に含める。**確認できなかったことを削除の根拠にしない。** 確認が落ちた週はゴーストが1回出るが、それは次の週に取り返せる。誤って消した行は戻らない。
- 候補が全滅した週は7件に満たないまま投稿する。候補を取り直して埋めることはしない。
- **リポジトリ全体の一覧取得（Trees API、Contents APIのディレクトリ一覧）は使わない。**

## なぜ全件同期にしないか

孤児行が害をなすのは、ダイジェストに出た瞬間だけである。出ていない孤児行は、テーブルに何行あっても誰も見ない。守る対象は毎週の7件であるのに、全件同期はテーブル全体を正すためにリポジトリ全体を走査する。この非対称が、そのまま余計なリスクになる。

外部仕様を確認した結果、面倒はいずれも全件走査の側にだけ付くことが分かった。

- **Contents APIのディレクトリ一覧は使えない。** 1ディレクトリあたり1,000ファイルが上限で、超えたことを応答が知らせない（[Get repository content](https://docs.github.com/en/rest/repos/contents?apiVersion=2022-11-28)）。打ち切りの表示が無い一覧を根拠に行を消すことはできない。保存先がフラットなので最も素直に見える経路が、最も危ない。
- **Trees APIは打ち切りを `truncated` で知らせるが、上限が2つある。** 「The limit for the tree array is 100,000 entries with a maximum size of 7 MB when using the recursive parameter」（[Get a tree](https://docs.github.com/en/rest/git/trees?apiVersion=2022-11-28)）。7MBの読み取り上限が `recursive` 指定時のものであることはGitHub側の回答でも確認できるが（[community discussion #23748](https://github.com/orgs/community/discussions/23748)）、100,000エントリの上限が非recursiveにも及ぶかは明記が無い。**上限の効き方を確定できない一覧を、削除の根拠にはしない。**
- **D1側にも制約がある。** bound parameterは1クエリ100個まで、SQL文は100,000バイトまで（[D1 limits](https://developers.cloudflare.com/d1/platform/limits/)）。差分をそのまま `IN (?, …)` へ並べられないので分割が要る。

実在確認は対象が常に10件前後なので、この3つのどれにも当たらない。分割も打ち切り判定も要らず、実装を誤ったときに消える行も候補数に収まる。

もう1つ根拠がある。**投稿の直前に候補を1件ずつ外部へ問い合わせて落とす処理は、既に同じ経路にある。** サムネイルの検証（[ADR 0011](0011-digest-rows-with-excerpt-and-thumbnail.md)）が、各行の画像URLを取りにいって取れないものを落としている。実在確認はその隣に同じ形がもう1つ増えるだけで、新しい構造を持ち込まない。

## 検討した代替案

- **週次cronの中でTrees APIと全件突き合わせる**: テーブルが常に正しくなり、GitHubにあってD1に無いクリップも拾える。採らない理由は上記のとおりで、守る範囲に対して走査が広すぎ、実装を誤ったときの失敗が「台帳の全行削除」になる。ADR 0010 が挙げた可用性の懸念自体は、突き合わせを失敗してもよい前処理にすれば消えるので、却下の理由には数えない。
- **別スケジュールのcronで全件突き合わせる**: ダイジェストの可用性からは切り離せるが、走査に伴うリスクは変わらないまま、実行経路と失敗しうる場所が1つ増える。
- **GitHubのpush webhookで即時反映する**: 削除もリネームも正確に拾え、遅延も無い。ただし公開エンドポイント、webhook secret、購読設定が増える。週1回しか読まないものに即時性の価値が無い。
- **孤児行を消さず `dismissed_at` を打つ**: 「片付けた」という利用者の操作の記録に、システムが書いた値が混ざる。正本が消えている以上、注釈だけ残しても注釈する対象が無い。
- **何もしない（ADR 0010 のまま）**: 実害が1回に収まるという前提が成り立たない。

## 影響

- **GitHubで消したクリップは、次のダイジェストから出てこない。** 台帳の行もそのとき消える。
- **消えた行は戻らない。** その記事を再び保存すれば新しい行として入るが、以前の `dismissed_at` と `last_shown_at` は失われる。
- **GitHub上でファイル名を変えると、片付け済みのクリップでもプールへ戻る。** 台帳の主キーがパスなので、リネームは「消えた1件」と「見たことのない1件」になる。実在確認が前者を消し、次の保存が後者を入れる。整理のためのリネームが記事を呼び戻す。パスではなくフロントマターのURLを鍵にすれば避けられるが、それには全ファイルの読み出しが要る。
- **週次の経路にGitHub App認証とContents APIが入る。** 失敗しても投稿は続くので可用性は下がらないが、GitHubが不調な週は確認が飛び、ゴーストが1回出ることがある。
- **週1回、10件前後のリクエストが増える。** GitHub Appのレート制限に対しては無視できる量である。
- **実在確認は保存時と同じContents APIのGETを使うため、本文まで取ってくる。** 存在の確認だけならHEADで足りるが、そのために別の経路を足すほどの量ではない。増えるのは週1回・記事10件ぶんの転送である。
- **候補が全滅した週は7件に満たない。** ADR 0010 の「毎回ちょうど7件」はここで崩れる。
- **GitHubにあってD1に行が無いクリップは、依然としてダイジェストに永久に出てこない。** ADR 0010 の影響欄が挙げたこの不整合は、この決定では直らない。復旧路は従来どおり `scripts/backfill-clips.ts` の手動実行だけである。
- **ダイジェストのテストがGitHubのモックを要求するようになる。** 投稿の経路にGitHubが入るため、既存のテストにもインストールトークンとContents APIの応答が要る。
