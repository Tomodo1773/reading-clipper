# ADR 0010: 未読の週次通知のため、読書状態を `dismissed_at` の1ビットとしてD1に持つ

- ステータス: Accepted
- 日付: 2026-08-16

## 背景

README.mdは「未読・既読状態の管理」と「未読記事の定期通知と推薦」を初期バージョンに含めないものとして挙げ、未読・既読管理には「数週間または数か月後に記事を再発見して状態を変更できる恒久的な操作導線」が要るとして、それまで読書状態のデータ設計を行わないと書いていた。

初期バージョンが動いた結果、保存は容易になったが、元の課題である「保存したまま読まれずに残る」はそのまま残っている。保存先が複数のブックマークからGitHubの1か所へ移っただけで、読まれない量は変わらない。

[ADR 0007](0007-thread-history-in-durable-object.md) は、定期実行（未読の通知）が必要になった時点でCloudflare Agents SDKを再検討すること、クリップ全体を横断する索引が必要になったらGitHub側かD1側に作ることを、いずれも将来の論点として残していた。この2つが同時に必要になった。

設計の出発点として、次を確認した。

- `GET /repos/{owner}/{repo}/git/trees/{sha}?recursive=1` は fine-grained permission の `Contents: read` で呼べ、リポジトリ内の全パスを1リクエストで返す。[ADR 0005](0005-title-based-file-name-and-plain-body.md) でファイル名を記事タイトルそのものにし、`clips/{host}/` にホストを含めたため、**クリップの母集団とタイトルとホストは、GitHubだけからほぼ無料で列挙できる**。
- 一方、フロントマターの中身（`source_url` など）を読むには全ファイルのGETが要る。列挙はO(1)リクエストだが、フロントマターの読み出しはO(N)リクエストになる。

## 決定

### 状態

- 読書状態は `dismissed_at`（NULL可のタイムスタンプ）**1ビットのみ**とする。`unread` / `reading` / `read` / `archived` のような状態機械を持たない。
- この1ビットを「既読」と呼ばない。UIのラベルは「片付ける」など、**読んだかどうかを主張しない語**にする。挙動は同じだが、「既読」と名付けると既読取り消し・読了率・「読んだけど後でまた読む」といった機能を後から呼び込む。名前が縛るのはスキーマではなく将来の設計判断である。
- この規則はボタンのラベルだけでなく、**ダイジェストの見出し・通知文・スレッドへ書き込む文にも及ぶ**。「未読」もまた読んだかどうかについての主張であり、片付け忘れた既読の記事に対して偽になる。実装では「まだ片付いていないクリップ」で通す。機能そのものの呼び名としての「未読の週次通知」（README.md）だけは、外向きの説明として残す。
- Dismissを理由別（「読んだ」／「興味ない」など）に割らない。ボタンは1つ。

### 保存場所

- 正本はCloudflare D1。テーブルは1つ、列は5つ。

  ```sql
  CREATE TABLE clips (
    path          TEXT PRIMARY KEY,  -- clips/{host}/{title}.md
    url           TEXT,
    clipped_at    TEXT NOT NULL,
    last_shown_at TEXT,
    dismissed_at  TEXT
  );
  ```

  タイトルは `path` の末尾から取れるので列に持たない。`url` は保存時にはただで手に入るが、フロントマターから読み直すのは高いので複製する。
- **D1はクリップの台帳ではなく、GitHubに対する注釈レイヤーと位置づける。** 本文・タイトル・ホストの正本はGitHubにあり、D1が失われても母集団はTrees APIから再構成できる。失うのはDismissと提示の記録だけである。
- GitHubから手でファイルを消したときにD1へ孤児行が残るが、**ダイジェスト生成時にTrees APIと突き合わせることはしない。** 孤児行はダイジェストに1度出たあと「片付ける」を1回押せば二度と出てこないので、実害が1回の表示に収まる。突き合わせを入れると、cronの経路にGitHub App認証とTrees APIの取得が丸ごと増え、ダイジェストがGitHubの障害で落ちるようになる。Trees APIを使うのはバックフィルと復旧のときだけにする。

### 週次ダイジェスト

- 日曜9時（JST）にSlackのDMへ1通投稿する。Cloudflareのcronトリガーは**UTC指定**なので `0 0 * * SUN` を `wrangler.jsonc` の `triggers.crons` に書き、`scheduled` ハンドラを `fetch` / `queue` と同じ既定エクスポートへ足す。曜日フィールドは `1-7` / `MON-SUN` で、標準的なcronの `0`（日曜）は `invalid cron string` で拒否される。
- `scheduled` にはSlackのイベントが無く、投稿先の `channel` が手元に無い。**`conversations.open` に `users: SLACK_ALLOWED_USER_ID` を渡して毎回引く。** DMのチャンネルIDをsecretとして持つ案もあるが、既にある `SLACK_ALLOWED_USER_ID` から導ける値のために管理する値を増やさない。代償はBot Token Scopeへの `im:write` の追加とSlack Appの再インストールで、これは一度きりのコストである。
- 毎回**ちょうど7件**を出す。セクション分割をせず、件数を保存量に連動させない。

  ```sql
  SELECT path, url FROM clips
  WHERE dismissed_at IS NULL
  ORDER BY last_shown_at ASC, clipped_at DESC
  LIMIT 7;
  ```

  SQLiteは `ASC` でNULLを先頭へ置くため、この1本で「未提示が最優先／その中では新しい順／既提示は最も長く出していない順」が成立する。閾値も調整パラメータも持たない。
- 出した7件に `last_shown_at` を打つ。これが単純なラウンドロビンになるため、提示回数（`shown_count`）は持たない。打つのは**Slackへ投稿できてから**にする。cronは再試行されないので、選んだ時点で打つと、投稿に失敗した週の7件が一度も出ないまま順番の後ろへ回る。
- **未Dismissが0件のときも投稿する。** 無投稿にすると「片付いている」と「cronが落ちた」が受け手から区別できない。週1回の通知が来ないことは、この機能が静かに死ぬ最初の兆候そのものなので、そこだけは黙らせない。
- ダイジェストを投稿したら、そのメッセージの `ThreadAgent` へ内容を1ターン分書き込む。これによりスレッドで「3番目のやつ片付けて」と言われたときにAIが対象を特定でき、`list_clips` のような追加ツールが要らなくなる。
- **この巡回そのものが、README.mdが要件とした「数か月後に記事を再発見する恒久的な導線」を兼ねる。** Dismissしない限りいつか必ず再登場するため、専用の検索UIや一覧画面を作らない。

### Dismissの入口

2つ持つ。どちらも同じ更新関数を呼ぶ。

| 入口 | 経路 | 対象 |
|---|---|---|
| ダイジェストの行ごとのボタン | `/slack/interactivity` → 直接D1を更新 → `chat.update` で元メッセージを書き換える | 単体 |
| スレッドでの自然文（「これ片付けて」） | 既存のQueue → AI → `set_clip_dismissed` ツール | 単体のみ |

- **ボタン押下はAIを経由させない。** `action_id` と `value` で意図が確定して届くものを、自然文へ落として再解釈させる利得が無く、レイテンシ・費用・「AIがツールを呼ばない」失敗モードだけが増える。[ADR 0006](0006-agent-with-save-tool.md) の「入力を事前分類しない」は自由文についての原則であり、ボタンは自由文ではないので抵触しない。
- Slackはインタラクティブpayloadも Events API と同じ `v0:{timestamp}:{rawBody}` で署名するため、`verifySlackSignature` をそのまま再利用する。allowlist検証（`team_id` / `user.id`）も同じ。bodyがJSONではなく `payload=` のform urlencodedである点だけ異なる。
- 二度押しに専用の冪等キーを持たない。`UPDATE clips SET dismissed_at = ? WHERE path = ?` は2回目も同じ状態を書き直すだけで、`action_ts` を記録するテーブルを足しても防げる事故が存在しない。
- 行そのものはSlackのpayloadに入っている `message.blocks` をそのまま使い、組み立て直さない。ただし**どの行を残すかはD1へ問い直す。** 続けてボタンを押すと、2回目のpayloadには1回目の `chat.update` が届く前の `blocks` が入っているため、押された行を引くだけの差分で作ると、片付けたばかりの行がボタンごと書き戻る。7件を続けて押すのが想定された使い方である以上、これは例外ではなく通常の経路にあたる。
- **一括Dismissボタンは作らない。** 7件を7回押すコストは許容範囲であり、一括で捨てたくなるほど不要なものは、そもそも保存しない。
- **AI経由は単体のみとし、一括を扱わせない。** ツールは `set_clip_dismissed(path, dismissed)` の1本で、`false` を渡せば戻せる。確認プロンプトは設けない。

### バックフィル

既存クリップは、Trees APIでパス一覧を取り、`clipped_at` に実行時刻、`url` にNULLを入れて流し込む。`url` がNULLの行はGitHubのファイルへリンクする。フロントマターは読まない。

`scripts/backfill-clips.ts` はパス一覧を標準入力から受けてSQLを書き出すだけにし、GitHubの認証を持たない。一覧の取得は `gh api` に任せる。**このスクリプトは使い捨てにせず残す。** D1を失ったときに母集団を作り直す唯一の導線がこれであり、初回のバックフィルと復旧は同じ操作だからである。

### 記録しないもの

- Dismissの理由。
- スレッドで会話が発生したかどうか。当初これを最も強い興味の信号として記録する案を採ろうとしたが、**追加質問が出るかどうかは記事の完全性を測っており、興味の深さを測っていない**。必要なことが全部書かれた良い記事ほど質問が出ない。信号の向きすら確かでないものに配線を足さない。
- 保存からDismissまでの日数を専用の列として持つこと（`dismissed_at - clipped_at` で導出できる）。
- 追記専用のイベントテーブル。

## 検討した代替案

- **フロントマターを状態の正本にする**: 記事と状態が同じ場所にあり、追加のインフラが要らない。採らない理由は**未読の一括取得がO(N)リクエストになる一点**である。列挙自体はTrees APIで1リクエストなので安いが、`dismissed` の判定には全ファイルのGETが要る。副次的に、状態更新のたびにcommitが増えて本文のGit履歴が埋まる点も、ADR 0005 で「フロントマターの直下を本文そのままにする」と決めた構成と相性が悪い。なお当初は「`Contents` 権限ではSearch APIが使えないので列挙が重い」「shaによる楽観ロックの競合処理が要る」も理由に挙げていたが、前者は列挙がTrees APIで足りるため論拠にならず、後者も週1・単独ユーザーの書き込みでは実質発生しない。**理由を積み増すと、前提が変わったときに再評価できなくなる**ため、この2つは論拠から外す。
- **既読/未読という素直なモデルにする**: 「未読＝プールにいる／既読＝出た」と定義するなら `dismissed_at` と完全に同型で、実行時の挙動に差は無い。差が出るのは真理条件で、「既読」は過去の世界についての主張なので押し忘れ・押し間違いで偽になりうるが、「もう出さない」は押した本人が唯一の権威者なので押した時点で必ず真になる。実務上より重いのは前述の「将来の機能追加を呼び込む」ほうである。
- **Dismissを「読んだ」と「興味ない」の2種類に割る**: 将来の興味傾向の分析に使える。採らない理由は3つ。(1) 収集タイミングが最悪で、週末にダイジェストを片付けている瞬間は最も分類に興味がない瞬間である。(2) 現実の却下理由の多くは「興味はあるが、もう読まないと諦めた」であり、2択しかないとこれが両方へ散って**両方のラベルが汚れる**。1ビットの正直な記録より2ビットの汚れた記録のほうが後で害になる。(3) 迷った回は**何も押されない**ため、プールが減らず通知が無視され始める。1人サービスの最大のリスクは設計ミスではなく利用停止なので、この失敗モードが他のどの利点よりも重い。加えてこれは「後から取り返しがつかない」選択ではなく、必要になれば同じ列に値を足すだけで拡張できる。
- **状態を一切持たない**: 毎週Trees APIで全パスを取り、ランダムまたは古い順に7件出す。DBもボタンも要らない。ダイジェストの価値が「リストを空にすること」ではなく「思い出させること」なら、これで足りる可能性がある。採らない理由は、片付けた記事が延々と再登場し、**通知そのものを無視するようになる**ため。それは1人サービスの死因そのものである。この経路を通って初めて、1ビットが「通知が無視され始めるのを防ぐための最小限の介入」として正当化される。
- **提示回数だけ記録し、3回出しても手が付かなければ自動的に外す**: 自己申告がゼロになる。ただし「その週たまたま忙しかった」だけの記事が静かに消え、本人が気づけない。消していいかの判断を機械に委ねると、リスト自体が信用できなくなる。
- **今週保存した分と積読から、それぞれN件ずつ出す**: 当初案。セクションごとに件数が独立するため、今週の保存をすべて片付けていると総量が落ちる。ダイジェストの価値が「今週の保存量」というコントロールできない変数に連動してしまう。定員制はこれを直したもの。
- **`ORDER BY shown_count ASC, last_shown_at ASC, clipped_at ASC` にする**: 提示回数の少ない順に取る。ただし初回実行時は全件が `shown_count = 0` なので `clipped_at ASC` が効き、**最も古い7件**が出る。昨日保存した記事は未提示の在庫がはけるまで何週間も出てこず、新規保存が飢餓状態になる。`last_shown_at ASC, clipped_at DESC` なら未提示の中で新しいものが先に出るため、この問題が起きない。
- **ボタン押下時に「〜をDismiss」という自然文を組み立ててAIへ渡す**: 経路が1本になり、新しい処理を書かずに済むように見える。ただし必要な `/slack/interactivity` エンドポイントはどちらの案でも要るため節約になるのは数十行だけで、代わりに確定した構造化データを壊してから復元する動きになる。
- **Workers KV**: 実装が最も軽い。ただし一覧の取得がprefix listしかできず、`dismissed_at IS NULL` での絞り込みと並べ替えを表現できない。結果整合の遅延もある。
- **Durable Objectに全クリップの索引を持つ**: 既にDOを使っているため追加のインフラが要らず、SQLiteも使える。ただし1スレッド単位で閉じているという ADR 0007 の設計と役割が食い違い、全クリップを1オブジェクトへ集約することになる。Cloudflareのストレージ選定ガイドはD1を「エンティティを横断して問い合わせる構造化データ」向けとしており、この用途は素直にD1にあたる。
- **Cloudflare Agents SDKの `this.schedule` を使う**: ADR 0007 が再検討先として挙げていた。ただし今回必要なのはスレッドに紐づかない週1回の定期実行であり、Workers標準のcronトリガーで足りる。SDKを入れる理由にならない。
- **月次でDismiss済みと会話したクリップのタイトルをモデルへ渡し、興味傾向の所見を書かせる**: README.mdが挙げる「興味傾向の分析」を、統計ではなくモデルの読解で満たす案。筋は通るが、いま読む側が存在しない。必要になった時点で、`clips` テーブルとGitHubのタイトルから後追いで実装できる。

## 影響

- **正本が2つに割れる。** GitHubのファイルとD1の行が対応しなくなりうる。GitHubから消したクリップの孤児行は1度だけダイジェストに出るが、逆にD1へ登録されないままGitHubにだけ存在するクリップ（保存には成功したがD1のINSERTに失敗した場合）は、**ダイジェストに永久に出てこない**。この不整合を検出する手段は持たない。バックフィルを流し直せば拾えるが、その必要があることに気づく手段が無い。
- **D1を失うとDismiss済みかどうかが分からなくなる。** 母集団はTrees APIから復元できるが、片付けたはずのものが全部戻る。バックアップの導線は持たない。
- **興味傾向の分析の材料を今は持たない。** Dismissの理由も、読んだかどうかも記録しない。将来分析したくなったとき、それ以前の期間について理由は遡れない。判断としては、いま取れるデータは自己申告バイアスと文脈の悪さで質が低く、無いより悪いと考えた。
- **7件/週を消化しきれなければ、プールは増え続ける。** 保存が週7件を超え、かつDismissが追いつかなければ、ダイジェストは減らないまま回る。上限も警告も設けない。
- **通知が無視され始めても検出できない。** この機能が死ぬときは静かに死ぬ。Dismiss率が落ちていることを知らせる仕組みは持たない。
- **Slack Appの設定が2つ増え、再インストールが要る。** Interactivity & Shortcuts を有効化してRequest URLに `/slack/interactivity` を登録し、Bot Token Scopesへ `conversations.open` のための `im:write` を追加する。スコープの追加にはSlack Appの再インストールが伴う。この手順はREADME.mdの実装手順へ追加する。
- **AIがD1を書き換えられるようになる。** ADR 0006 と ADR 0009 が指摘したとおり、モデルの文脈には記事本文とWeb検索結果という第三者の書いたテキストが入っている。`set_clip_dismissed` はGitHubを書き換えないうえ、単体のみ・可逆・実行結果が返信に現れるため、README.mdが求める「実行前にSlackで確認を取る導線」は設けない。**一括操作をAIへ渡さないことがこの判断の前提**であり、将来 `dismiss_all` のようなツールを足すなら確認導線の要否を再評価する。
- **`wrangler.jsonc` にD1バインディングとcronトリガーが増える。** D1の無料枠は1日あたり読み取り500万行・書き込み10万行で、週1回のクエリと数件の更新には桁違いに余裕がある。
- **クリップ数がTrees APIの上限を超えると壊れる。** 100,000エントリまたは7MBを超えると `truncated` が返る。個人利用の規模では当面到達しないが、バックフィルと復旧はこの上限に依存している。
- **D1の `database_id` を公開リポジトリへ置く。** 共通ポリシーは実環境固有のIDをコミットしないと定めているが、`wrangler.jsonc` のbindingをsecretで渡す手段が無く、Workers Buildsからのデプロイに実値が要る。単体では権限を持たず、Cloudflareのドキュメントも設定ファイルへの記載を前提としているため、`AI_GATEWAY_ID` と同じ扱いの例外とする。**この例外はD1バインディングに限る。** アカウントIDやトークンには広げない。
- **保存し直してもDismissは戻らない。** 同じURLをもう一度送るとGitHubのファイルは上書きされるが、`dismissed_at` は保持される（`INSERT OR REPLACE` にしないのはこのため）。「もう一度保存した」を興味の再燃と読んで自動的に戻す案もあるが、片付けた記録を保存操作の副作用で消すことになるので採らない。戻したいときは会話で `set_clip_dismissed` に `false` を渡す。この挙動は利用者に見えないので、忘れた頃に「保存したのにダイジェストへ出てこない」と映る。
- **D1のスキーマ適用は手動になる。** Workers Buildsのdeploy commandは `wrangler deploy` で、migrationを適用しない。Queueの作成と同じくローカルからの手動操作として README.md の表に載せる。テーブル1つ・列5つに `migrations_dir` の運用を持ち込まない。
- Slackの1メッセージあたりのブロック上限は50。7件×（セクション＋ボタン）はこれに収まる。件数を増やす場合はこの上限を確認する。
