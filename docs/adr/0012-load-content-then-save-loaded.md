# ADR 0012: 保存するURLを、ロードした内容を見てAIが指す

- ステータス: Accepted
- 日付: 2026-08-17

> 更新: `load_content`と`save_loaded`を分ける判断は維持する。一時保存をターン内Mapへ置く判断と`save_loaded(url)`の入力は[ADR 0022](0022-persist-tool-refs-in-durable-object.md)で変更し、owner単位のDurable Objectに置く`loaded_ref`を使う。

## 背景

`save_clip` は渡されたURLをそのまま保存する。しかしSlackへ届くURLは、保存したい記事そのものを指しているとは限らない。実運用で2種類のずれが出た。

**中継ページ。** スマートフォンのGoogleアプリで記事を共有すると `https://share.google/...` が送られる。保存先リポジトリの `clips/share.google/` に2件残っている。実体はZennとDevelopersIOの記事だった。

**紹介ポスト。** Xで技術ブログが紹介されているのを見つけたとき、そのポストを共有するのが一番簡単な操作になる。しかし「この記事よかった」という一言とURLだけのポストを保存しても意味がない。欲しいのはリンク先の記事である。

### 直接の機序

`saveClip` は `canonicalizeUrl(rawUrl)` の結果を `buildClipPath` と `recordClip` に渡し、フェッチャーが返す `FetchedContent.canonicalUrl` を読んでいない。そのため中継URLでは次が同時に壊れる。

- `classifyUrl` が `web` を返すので、Zenn専用フェッチャーが動かずFirecrawl経由の劣化版が保存される
- フロントマターの `source_url` とD1の `url` が中継ページを指す
- `clips/share.google/` にファイルが置かれる
- 同じ記事をZennの直リンクで送り直すと、上書きされずに別ファイルとして増える

なお本文自体は正しい記事が入っている。Firecrawlがリダイレクトを追っているためで、**壊れているのは識別（どのURLの記事か）だけ**である。

### 実測

| 対象 | 結果 |
|---|---|
| `share.google/{id}` | 302 → `www.google.com/share.google?q={id}` → 301 → 記事本体。**素のHTTPリダイレクト2段であり、JavaScriptの中継ページではない**。User-Agentによる差も無い |
| 同上（HEAD） | **中間ホップがHEADに `200 OK` を返して止まる。** GETにだけ `301 + Location` を返すため、リダイレクト解決にはGETが要る |
| `x.com/i/web/status/{id}` | `x.com/{username}/status/{id}` へ1回リダイレクト。200でHTMLが返り `og:image` も入っている |
| 存在しないZenn / Qiita / X記事 | すべて404。**トップページへリダイレクトされることはない** |

`rel="canonical"` や `og:url` のパースは要らない。Xのリダイレクト先は `canonicalizeUrl` が `/i/web/status/{id}` へ書き戻すため同じ正規形に収束する。

### 問題の核心

この2つは「入力URLと保存したいURLが違う」という同じ形に見えるが、決着しなかったのは分類が違うからではない。**`save_clip` の中で「読む」と「置く」が癒着していることが原因である。**

癒着しているため、**中身を読まないと分からないこと（これは紹介ポストか、それ自体が読み物か）を、読む前に決めなければならない**という不可能を要求していた。「下見用のツールをいつ呼ぶか」をAIに判断させる設計は、どれもこの不可能を別の場所へ移しただけだった。

## 決定

### ツールを2つに分ける

| ツール | やること | してはいけないこと |
|---|---|---|
| **`load_content(url)`** | リダイレクトを解決し、着いた先で種類を判定し、その種類の取り方で本文を取る。**全文を返す。** 取得結果をターン内のメモへ置く | GitHubにもD1にも一切書かない。中身の意味で行き先を変えない |
| **`save_loaded(url)`** | **このターンでロード済みのもの**を、ロードしたときの本文のままGitHubとD1へ書く | 取得しない。URLを差し替えない。**未ロードのURLは拒否する** |

名前は順序を示すために選んだ。`save_loaded` は前提条件そのものを名前で言っている。

### ロードを無条件にする

**「このURLは中身を見ないと分からないタイプか?」という判断を、設計から消す。** URLの文字列だけでは答えられない問いだからである。

この判断を残すと、その基準は「SNSの投稿やブックマークのエントリページは怪しい」というサイト知識になり、コードかプロンプトのどちらかにホストの一覧を抱えることになる。外せば紹介ポストの取り違えが確率で再発する。

ロードを無条件にすれば、AIが判断するのは**読んだ結果に対してだけ**になる。証拠を見てからの判断しか残らない。

### アプリが従ってよい境界

| 従ってよい | 従ってはいけない |
|---|---|
| **プロトコルがそのURLの意味だと言っていること。** 301は「この資源はここへ移った」というサーバー自身の宣言であり、追わないほうが仕様違反になる | **中身が意味していること。** 「このポストは記事を紹介している」という解釈 |

`share.google` は前者、Xの紹介ポストは後者。この線を引けば両者が同じ穴に落ちない。

リダイレクトを追うのはURLを差し替える行為ではなく、「そのURLを取得する」の定義そのものである。現に既存コードもFirecrawlも追っていて、**追った結果を捨てているだけ**だった。そのうえで `load_content` は着いた先のURLをAIへ返すので、最終的に保存されるのは**AIが明示したURL**になる。アプリがAIの指示を上書きする状態は構造的に起きない。

### 戻り値の割り方

- **`load_content` が全文を返す。** 切り詰めた分で「記事か紹介か」を判断させる理由がない
- **`save_loaded` は結果だけを返し、本文を返さない。** 本文がツール結果として会話に現れるのは1回だけになる
- **取得は1回だけ。** `load_content` が取った全文をターン内のメモに置き、`save_loaded` はそれを読む。入力URLと着いた先のURLの両方をキーにする

ADR 0006 は「要約と掘り下げの根拠は本文にしかないので `save_clip` が本文を返す」と決めた。その要請は `load_content` が満たす。**ADR 0006 のうち本文の出どころだけがここで変わり、本体（入力をURLの有無で分岐しない・保存はツール・失敗はツール結果）は変わらない。**

### 一時保存はターン内のメモリに置く

`createTools` のクロージャに `Map` を1つ持つ。両ツールは同じターン・同じisolateで動くため、KVもCache APIも要らない。

Durable Objectへ置く案は採らない。会話履歴としてすでに本文が入っており、同じものを2箇所に持つことになる。

代償は、**ロードした次のメッセージで「保存して」と言われるとメモが消えていること**である。その場合 `save_loaded` が拒否し、AIがロードし直す。取得が1回増えるだけで壊れない。この経路は稀だと判断した。URLを転送してくる時点で保存の意図があり、中身だけ見て保存を迷う場面は実際には起きない。

### 保存するかどうかをAIに迷わせない

システムプロンプトの「URLが含まれていても保存の依頼とは限らない」を反転させ、**URLが来たら基本は保存する**を既定にする。

「保存するか迷うから中身だけ見たい」という場面は、このサービスでは起きない。読ませてヒアリングしている時点で実質その記事を読んでおり、それなら保存しておくほうが筋が通る。

例外は1つだけ残す。**読んだ結果が記事でなかったとき**（ログイン画面、同意画面、中身のない中継ページ）。これは意図の判断ではなく内容の判断なので、全文が手元にあるAIが正しく下せる。

結果としてAIが決めるのは2つになる。

- **何を保存するか**（ロードしたものが本命か、リンク先が本命か）
- **そもそも記事だったか**（違えばその事実を返す）

### 順序は3層で担保する

名前だけに保証させない。

1. **名前** — `load_content` → `save_loaded` で順序を示す
2. **説明文** — `save_loaded` は「ロード済みのものだけを保存する」と明記する
3. **拒否** — 未ロードのURLでは取得も保存もせず、その事実を返す。**唯一の保証はここで、テストで固定できる**

拒否されたAIはロードし直して呼び直せばよく、同じターン内で回復する。

### ステップ上限

`MAX_STEPS` を 5 から 8 へ上げる。紹介ポストの経路が「ロード → ロード → 保存 → 返信」の4手になり、拒否からの回復や複数URLで足りなくなるため。

## 検討した代替案

- **`save_clip` の中で小さくLLMを呼び、リンク先が本命かを判定する**: エージェントのステップを消費せず、ホストの列挙も要らない。採らない理由は、**判断が会話に現れないこと**。ツールの中で下された判断は利用者から見えず、外れても訂正する経路がない。エージェントがすでに持つ能力をツールの内側で複製することにもなる。非決定的な要素はエージェント1個に集約する。
- **取得の中で決定的に委譲する**（`article` / `note_tweet` が無く外部リンクが1本だけならリンク先を取る）: LLMを増やさず10行程度で済み、テストで固定できる。「本文が短く実質が外部リンク1本」という条件はサイト非依存に書けるため、サイトごとのコードにもならない。採らない理由は2つ。**アプリがAIの指したURLとは別のURLを保存することになる**（プロトコルの宣言ではなく中身の意味に基づく差し替えで、上の境界の向こう側にある）。そして**この設計の下ではAIが全文を読んでいるため、検出器を置いても情報が1ビットも増えない**。正しくても冗長な機構は入れない。
- **`save_clip` の内部でリダイレクトを解決し、着いた先を保存する**: 変更が小さく、中継ページは直る。採らない理由は、**AIが着いた先を知らないまま保存が済むこと**。会話に何も残らないため、転送先が意図しないページだったときの訂正の起点がない。ロードを分ければ同じ利益が会話に見える形で得られる。
- **モデル呼び出しの前処理として、メッセージ本文中のURLを転送先へ書き換える**: 中継ページを決定的に解決でき、AIは中継URLを一度も見ない。採らない理由は、解決の機構が「前処理」と「ロード処理」の2箇所になること（ADR 0011 の「同じ値の出どころを2本に割らない」に反する）。さらに前処理は**本文を1文字も見ていない時点**で走るため、紹介ポストには原理的に何もできない。問いの半分にしか触れない機構のために、ADR 0006 が廃止した入力パスでのURL抽出を復活させる割に合わない。
- **保存せずに中身を見るだけのツールを、任意の下見として足す**: 直リンクの経路は1手のままにできる。採らない理由は、AIが「このURLは下見が要るか」を**本文を見る前に、URLの見た目だけで**判断することになるため。その基準はプロンプトに書くしかなく、実質サイトの一覧がプロンプトへ移る。呼び忘れれば紹介ポストの取り違えが再発する。ロードを無条件にすればこの判断ごと消える。
- **下見ツールが本文の先頭だけを返し、保存ツールが全文を返す**: 本文を入力として抱えるモデル呼び出しが1回で済む。採らない理由は2つ。**切り詰めた分で「記事か紹介か」を判断させることになる**。そして**保存ツールが「書く」と「本文を届ける」の二役を持ち続ける**ため、今回外そうとしている癒着が場所を変えて残る。
- **楽観的に保存してから、結果に外部リンクを添えて次のターンで訂正させる**: 新しいツールが要らず、変更が最小で済む。採らない理由は、**紹介ポストのクリップが必ず1件書かれ、それを消す手段がないこと**。クリップの削除は初期バージョンの対象外で、片付けの印はダイジェストから消すだけでファイルはリポジトリに残り続ける。
- **経由したURLをフロントマターに `via_url` として残す**: 委譲が非可逆でなくなり、誰が紹介していたかも残る。採らない理由は、フロントマターがデータベースではなく読むためのものであり、項目が増えると読むときの負担になること。経由したURL自体に、後から見返す価値がほとんどない。
- **一時保存をDurable Objectへ置く**: ターンをまたいで「さっきの保存して」が通る。採らない理由は、会話履歴として同じ本文がすでにDurable Objectに入っており、同じものを2箇所に持つことになるため。

## 影響

- **`FetchedContent.canonicalUrl` が保存先の決定に使われるようになる。** 保存先パス、`source_url`、D1の `url` がすべて取得結果側に切り替わる。同じ記事を別経路で送っても同じパスに落ちるため重複が減る。**フロントマターの項目もD1の列も1つも増えない。値が正しくなるだけである。**
- **モデルの往復が保存1件につき1回増える。** ロードのぶん。HTTPリクエストの本数は変わらない（記事ページのGETと本文取得は今も走っている）。
- **本文を入力として抱えるモデル呼び出しが1回から2回になる。** 保存を判断する回と、要約を書く回。本文がツール結果として現れるのは1回のままである。2回の呼び出しは本文までのプロンプトが同一なので、暗黙のプロンプトキャッシュが効く見込みだが実測はしていない。
- **ロードしたのに保存しない、という失敗が新しく生まれる。** 要約だけが返って保存されない。利用者には保存先リンクが無いことで見える。**見える失敗と見えない破損なら前者を選ぶ**（ADR 0011 と同じ判断基準）。
- **AIが読んでいないURLが保存されることは起こり得なくなる。** モデルが組み立てた実在しないURLもここで止まる。ロードした本文と保存された本文がズレることもない（同じメモから書くため）。
- **紹介ポストのクリップは作られない。** 記事だけが保存される。誰が紹介していたかは会話に残り、クリップには残さない。
- **ADR 0006 の「`save_clip` が本文を返す」が変わる。** 本文の出どころが `load_content` へ移るだけで、要約と掘り下げの根拠が会話に残るという保証は保たれる。
- **システムプロンプトが伸びる。** ロードした結果をどう判断するかを書く必要があり、その品質はテストで固定できない。順序そのものは `save_loaded` の拒否で固定できるが、保存を呼ぶ意思は固定できない。
- **既存の `clips/share.google/` のクリップは自動では直らない。** 同じURLを送り直せば正しい場所へ保存され直すが、古いファイルは残るため手で消す必要がある。
- **リダイレクトを追えない中継ページ（JavaScript遷移など）は解決できない。** その場合は中継ページ自体がロードされ、AIが本文を見て「記事がない」と気づく。黙って壊れることはない。
- **記事ページのGETを拒否されるサイトでは、着いた先が分からないまま続行する。** ロード処理は例外を投げず入力URLをそのまま使うため、中継URLなら現状と同じ結果になるだけで退化はしない。
