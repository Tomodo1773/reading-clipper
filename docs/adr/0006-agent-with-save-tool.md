# ADR 0006: Slackの入力をすべてAIへ渡し、保存をツールにする

- ステータス: Accepted
- 日付: 2026-08-16

## 背景

`/slack/events` は本文からURLを抽出し、1件でもあれば `ClipJob` をQueueへ送る。1件も無ければ「URLが見つからなかったよ」と返す。つまり届いたメッセージは常に保存指示として解釈され、それ以外の使い道が無い。

このBotで普通に会話できるようにしたい。将来は、保存したURLについて「ここには何が書いてあるのか」と掘り下げたり、GitHubに溜めたクリップを検索・整理させたりするところまで広げたい。

そのとき、URLの有無では意図が決まらない。`https://... これ前に読んだ気がするけどどう思う?` は保存指示ではなく、`これ後で読みたい https://...` は保存指示である。この判別条件をアプリ側の規則として書き続けると、条件が増え続けて破綻する。

加えて、保存という出来事が会話の中に現れないと、その後の掘り下げに繋がらない。アプリが黙って保存してアプリが返信を組み立てる形では、モデルから見て「何が起きたか」の記録がどこにも残らない。

## 決定

> ツールの構成は [ADR 0012](0012-load-content-then-save-loaded.md) で更新した。`save_clip` は `load_content` と `save_loaded` に分かれ、本文を返す役目は `load_content` へ移っている。以下のうち変わったのはその一点で、入力をURLの有無で分岐しないこと・保存をツールにすること・失敗をツール結果として返すことは変わらない。

- Slackから届いたメッセージは、URLの有無にかかわらずすべてAIへ渡す。受付Worker側でのURL抽出による分岐をやめる。
- 保存はモデルが呼ぶツール `save_clip(url)` にする。引数はURL1つだけで、保存する本文をモデルに作らせない。
- `save_clip` の中身は既存の処理をそのまま使う。`canonicalizeUrl` → `fetchContent` → `buildClipPath` → `getGitHubFile` → `renderClipMarkdown` → `putGitHubFile`。
- `save_clip` は保存の結果（`saved`、保存先のパスとURL、タイトル、`complete`）と、取得した本文をツール結果として返す。本文はトークン節約のために切り詰めない。上限は `fetchers.ts` の `MAX_CONTENT_CHARS`（200,000文字）のままとする。要約にも、その後の掘り下げにも、本文はここにしか入らないため。
- 要約はモデルがツール結果を読んで書く。要約専用のLLM呼び出し（`summarizeContent` / `parseSummaryResponse`、`response_format: json_object`、`temperature: 0.8`）を廃止し、`SUMMARY_SYSTEM_PROMPT` の中身（ADR 0004 の口調・長さ・禁止事項）はエージェントのシステムプロンプトへ移す。
- 保存の成否とGitHubのURLもモデルに書かせる。アプリが固定文を足す `formatSuccessReply` / `formatPartialReply` を廃止する。SlackのmrkdwnリンクがMarkdownと異なること（`<URL|ラベル>` であって `[ラベル](URL)` ではない）はシステムプロンプトに書く。
- `failureReply` は残すが、用途を「モデルに到達する前に落ちた場合」に限る。Queueメッセージが壊れている、LLMの呼び出し自体が失敗した、といった、返事を書くモデルがいない経路のためのもの。
- URLだけのメッセージを特別扱いしない。`tool_choice` の固定も、アプリ側でツール呼び出しのターンを合成することもしない。経路は1本にする。
- 取得した記事本文とツールの返り値は、指示ではなくデータとして扱う。破壊的なツール（GitHubの削除・リネームなど）を将来足すときは、Slackで確認を取ってから実行する。

## 検討した代替案

- **URLを検出したら従来の保存処理へ分岐し、それ以外を会話へ回す**: 現行コードの変更が最小で済み、保存が決定的なままになる。ただし「URLが含まれるが保存指示ではない」を判別する条件をアプリ側に書き続けることになる。保存の出来事が会話に残らないため、掘り下げの質問にも繋がらない。
- **URLだけのメッセージはアプリ側で処理し、ツール呼び出しのターンを合成して履歴に入れる**: 現行と同じくLLM呼び出し1回で済み、履歴の見た目も揃う。ただしシステムプロンプトとツール定義を共有していても経路が2本になり、保存の記録の作り方が2通りになる。節約できるのは本文を含まない小さなLLM呼び出し1回で、複雑さに見合わない。
- **`tool_choice` で `save_clip` を強制する**: URLだけを送ったときの決定性を保証できる。ただしツールの説明が明確なら現行のモデルは呼び忘れず、むしろ「そのURLについて話したいだけ」の場面でも保存が走る副作用の方が大きい。
- **保存とは別に、要約専用のLLM呼び出しを残す**: 要約の口調と長さを型（`{"summary": "..."}`）で縛れる。ただし本文を2回モデルへ渡すことになり、要約の文脈と会話の文脈が分かれる。掘り下げのときに「さっき君が言った要約」が会話に存在しないことになる。

## 影響

- **最初のターンのLLM呼び出しが1回から2回に増える。** 1回目はツール呼び出しを決めるだけで、入力に記事本文は含まれない。
- **保存が確率的になる。** URLだけを送ったときにモデルが `save_clip` を呼ばない可能性は残る。決定的だった動作を、ツールの説明とシステムプロンプトの品質に預ける。
- **要約の形式をアプリで保証できなくなる。** ADR 0004 の「1〜2文、60〜120字程度」はシステムプロンプトの指示になり、型による強制が無くなる。極端に長い返信や、Slackのmrkdwnではないリンク記法が出る可能性がある。
- **保存の成否の記述をモデルが書く。** 完了条件「Slackの返信から、保存に成功したか失敗したかを判別できる」は、ツール結果の `saved` をモデルが正しく読むことに依存するようになる。
- 「URLが見つからなかったよ」の即時返信が無くなる。URLの無いメッセージも通常の会話としてQueueへ入り、処理Workerが返信する。3秒以内のACKは変わらないが、返信までの時間は延びる。
- `ClipJob` は保存専用の形をやめる。Queueに残る旧形式（`version: 1`）は移行期間だけ受け付ける。
- 記事本文がモデルの文脈に入る。取得先は利用者が指定したURLだが、書いたのは第三者であり、信頼できない入力がツールを持つモデルの文脈に混ざる状態になる。現時点のツールは `save_clip` だけなので実害は小さいが、破壊的なツールを足す時点で確認フローが必須になる。
