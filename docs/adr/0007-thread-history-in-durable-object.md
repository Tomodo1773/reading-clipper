# ADR 0007: スレッドの会話履歴をDurable Objectにツール結果ごと持つ

- ステータス: Accepted
- 日付: 2026-08-16

> 更新: 会話履歴を無期限に保持する判断は[ADR 0022](0022-persist-tool-refs-in-durable-object.md)で変更し、90日を超えたturnと処理済みeventをAlarm APIで削除する。

## 背景

[ADR 0006](0006-agent-with-save-tool.md) でSlackの入力をすべてAIへ渡すことにしたが、Slackのイベントは1通ごとに独立したWorkerの起動であり、ターンをまたぐ状態がどこにも無い。

記事の内容は `save_clip` のツール結果に入る。これを保持しないと、2ターン目以降で本文を得るために毎ターン `save_clip` 相当を呼び直すことになる。呼び直す先が元サイトならFirecrawlで最大60秒、GitHubから読み直す形にしても、ツール呼び出しのためのLLM往復が毎ターン1回余分に増える。掘り下げて質問するという用途に対して、これは無駄が大きい。

会話履歴の置き場所として、Slackのスレッドを `conversations.replies` で読み直す案を検討した。追加のインフラが要らず、ユーザーが読む記録とも一致する。しかしテキストしか復元できず、ツール結果（記事本文、保存先のパス）が失われる。それではモデルは自分の過去の文章から保存先を読み取ることになり、成立しない。加えて2025-05-29以降、Marketplace外で商用配布される新規アプリは `limit` の最大値・既定値が15、レート制限が1req/分に落ちる制限が入っており、このアプリに適用されるかが文面から確定できない。

もう一点、Cloudflare Queuesは既定でconsumerを並行実行する（`max_concurrency` を未設定にすると、プラットフォームが許す最大までスケールする）。順序保証もキー単位の分割も文書化されていない。同じスレッドへ立て続けに届いた2通が並行して処理されると、履歴の読み書きが競合するだけでなく、エージェントループが2本並走して両方がSlackへ投稿する。

## 決定

- スレッド単位のDurable Object `ThreadAgent` を置き、``idFromName(`${channel}:${thread_ts}`)`` で引く。
- 会話履歴は、モデルへ渡す `messages[]` の形のまま、`tool_use` / `tool_result` ブロックを含めてDOのSQLiteストレージへ保存する。

  ```sql
  CREATE TABLE turns   (seq INTEGER PRIMARY KEY AUTOINCREMENT, message TEXT NOT NULL, at TEXT NOT NULL);
  CREATE TABLE handled (event_id TEXT PRIMARY KEY, at TEXT NOT NULL);
  ```

  1つのDOが1つのスレッドに対応するため、`channel` と `thread_ts` の列は持たない。
- 追記のみとし、過去のターンを書き換えない。読んで足すだけなので、履歴の再構成とその競合を持ち込まない。前置きがバイト単位で安定するためプロンプトキャッシュにも乗りうるが、AI Gateway経由でプロバイダ側のプロンプトキャッシュが効くかは未確認であり、採用の理由には含めない。
- 記事本文は `tool_result` の中にあるので、2ターン目以降は取得も読み直しも行わない。GitHubへの保存は従来どおり行うが、会話のための読み出し口は持たない。
- 処理済みの `event_id` をDOに記録し、既処理なら破棄する。Cloudflare Queuesの配送保証はat-least-onceで、ドキュメント自身が冪等キーを持つことを推奨している。Slackのイベント再送もここで吸収する。
- 1ターンの実行はDO内で直列化する。DOのJSは単一スレッドだが `await` をまたぐと処理が交錯しうるため、`blockConcurrencyWhile` もしくは自前のPromiseキューで囲む。
- 受付Worker → Queue → 処理Worker（consumer）→ ThreadAgent DO の順は変えない。Queueは3秒ACKの分離と、再試行・dead letter queueのために残す。

## 検討した代替案

- **Slackのスレッドを正本にし、`conversations.replies` で毎ターン復元する**: 追加インフラが不要で、ユーザーが読める記録と完全に一致する。ただしテキストしか復元できずツール結果を保持できないため、本文を毎ターン取り直すことになる。`limit` が15に落ちる制限の適用可否も確定できない。なおSlack公式のBoltのAIアプリ実装例自体が、スレッドを読み直さずアプリ側の会話ストアを持っている。
- **Workers KV**: 実装が最も軽い。ただし結果整合で最大60秒の伝播遅延があり、直前のターンを読み落としうる。書き込みもlast-write-winsで、立て続けの2通でターンが消える。会話には向かない。
- **D1 と `max_concurrency: 1` の併用**: 強整合で、ターンを行としてINSERTすれば読み書きの競合も起きない。ただし直列化をQueue全体を絞ることで代用するため、URL保存を含むすべての処理が1本になる。Cloudflareのストレージ選定ガイドはD1を「エンティティを横断して問い合わせる構造化データ」向け、Durable Objectsを「per-user or per-customer SQL state」向けとしており、1スレッドの会話状態は後者にあたる。
- **Cloudflare Agents SDK（`agents` パッケージ）を採用する**: Durable Objectsの上に会話状態と `this.sql` を用意してくれる。ただしSDKの中心はWebSocketでのクライアント同期、`setState`、Reactフックであり、このアプリのクライアントはSlackなのでその部分の利得が無いまま、ライフサイクルの制約だけを受ける。SDKが載っている土台であるDurable Objectsを直接使う。将来 `this.schedule` 相当の定期実行（未読の通知など）が必要になったら再検討する。
- **記事本文だけ別に保管し、会話履歴はテキストだけ持つ**: 履歴を小さく保てる。ただし本文をGitHubから読み直す往復が毎ターン入り、さらに「このスレッドがどのクリップの話か」を別に記録する必要が出る。ツール結果ごと持てばどちらも不要になる。

## 影響

- **記事本文の分の入力トークンを毎ターン払う。** 20万文字を保存した場合、それがそのまま毎回の入力に乗る。掘り下げの往復が増えるほど線形に効く。プロンプトキャッシュで下げられる可能性はあるが、AI Gateway経由で効くか、モデル側のキャッシュ保持時間がこの用途（時間を空けてからの質問）に足りるかは未確認なので、コストの前提には置かない。
- **1つのスレッドに何本も記事を保存すると履歴が単調増加する。** 上限も退避も設けない。古いツール結果を差し替える方式は、追記のみという前提を崩し、プロンプトキャッシュに乗せられる可能性も捨てることになるため、必要になった時点で別途設計する。
- **会話の内容がCloudflare側にも残る。** GitHubのprivate repositoryに加えて保持場所が増える。削除の導線は持たない。
- **Slackのスレッドは状態の正本ではなくなる。** ユーザーがSlack上でメッセージを消しても、DOの履歴からは消えない。逆にDOのデータを失った場合、対話は復元できない。
- **スレッドをまたいだ検索はできない。** DOは1スレッド単位で閉じており、横断クエリの手段を持たない。将来クリップ全体を検索するときは、GitHub側かD1側に別の索引を作る。
- `wrangler.jsonc` にDurable Objectsのバインディングと `new_sqlite_classes` のmigrationが増える。1オブジェクトあたりのストレージ上限は10GB（Workers有料プラン）、key+valueは2MB。日本語20万文字はUTF-8で約600KBなので収まる。
- Durable Objectsのストレージ課金が2026年1月から始まっている。
