# ADR 0005: 保存Markdownは記事タイトルのファイル名にし、フロントマターの直下を本文そのままにする

- ステータス: Accepted
- 日付: 2026-08-16

## 背景

保存先は `clips/{host}/{pathSlug}-{URL hash}.md` で、`pathSlug` はURLのパスを英数字だけに落とした文字列、`hash` はcanonical URLのSHA-256の先頭16桁だった。この形式は衝突しないが、ファイル名から中身が分からない。Zennの `abc123def456` のようにパス自体が無意味なサイトでは、ファイル名が完全に意味のない文字列になる。GitHubのファイル一覧を後から見返すときに、これが読めないことが実際の不満として出た。

保存する本文の側にも問題があった。`renderClipMarkdown` はフロントマターの後に `# {title}`、`[元URL](...)`、`## 要約`、`## 取得内容` を出力し、記事の本文はその下の階層に入っていた。取得した本文はほとんどの場合H1で始まるため、こちらが付けたセクションの中にH1が現れる不自然な構造になっていた。

`## 要約` は保存の副産物ではなく、機能も担っていた。`parseStoredClip` が保存済みファイルから要約を読み戻し、Slackが同一イベントを再送したときに、取得も要約もせずに保存済みの要約で返信していた。

## 決定

- ファイル名は記事タイトルだけから作り、`clips/{host}/{記事タイトル}.md` とする。URLハッシュのsuffixは付けない。
- 日本語のタイトルは日本語のまま残す。ローマ字化、英数字への縮退、小文字化はしない。長さの上限も設けない。
- 実務上ファイル名が壊れる要素だけを潰す。
  - Windowsが禁じる `< > : " / \ | ? *` と制御文字を除く。
  - 先頭のドット（隠しファイル化）と、末尾のドット・空白（Windowsで壊れる）を除く。
  - Windowsの予約デバイス名（`CON` `PRN` `AUX` `NUL` `COM1`〜`COM9` `LPT1`〜`LPT9`）は、拡張子が付いていても予約されるため、末尾に `_` を足して外す。
  - 連続する空白は `-` 1つにまとめる。CLIやgitで扱いやすくするため。
  - `.md` を含めて255バイトに収める。多くのファイルシステムとGitのパス構成要素の上限がこの値で、日本語はUTF-8で1文字3バイトになるため、文字数ではなくバイト長で数え、コードポイントの途中では切らない。
  - すべて取り除かれて空になった場合は `untitled` にする。
- 同一ホスト内でファイル名が衝突した場合は上書きを許容する。衝突回避の連番やハッシュは足さない。
- 保存するMarkdownは `---\n{フロントマター}\n---\n\n{取得した本文そのまま}\n` だけにする。見出し、元URLのリンク、セクションは足さない。
- AI要約は保存しない。フロントマターにも入れない。要約はSlackへの返信だけで使う。
- フロントマターから `summary_status` を削る。ファイルの中に要約が無い以上、その成否を記録しても指す対象が無いため。他の項目（`source_url` `source_type` `title` `author` `published_at` `clipped_at` `slack_event_id` `fetch_complete`）は保存した内容とその出所を説明するので残す。
- 保存済みファイルから要約を読み戻す経路（`parseStoredClip`）を削除する。Slackの再送も、通常どおり取得・要約・保存（上書き）・返信で処理する。
- ファイル名の決定に取得後のタイトルが要るため、処理順を「取得 → パス決定 → GitHubの存在確認 → 保存」に変える。存在確認は更新に必要な `sha` を得るために残す。

## 検討した代替案

- **タイトルのslugと短いハッシュを併記する**: 衝突を防ぎつつ読めるようになるが、意味のない文字列がファイル名に残るという元の不満がそのまま残る。
- **衝突時に連番を付ける**: 上書きを避けられるが、同じ記事の再取得なのか別記事の同名衝突なのかをファイル名だけでは判定できず、GitHub上に重複が積もる。同じURLの再取得が上書きになる現在の動作とも噛み合わない。
- **フロントマターに要約を持つ**: 再送時の短絡を保てるが、要約は保存物ではなくSlackへ返す一言だという整理と合わない。複数行のテキストをフロントマターへ入れる分、パースも壊れやすくなる。
- **`## 要約` セクションだけ残して他を消す**: 階層構造が邪魔だという不満の中心がこのセクションなので、採らない。

## 影響

- **衝突耐性を失う。** 同じホストで同じタイトルの別記事をクリップすると、後から送った方が前のファイルを上書きする。URLが違っても検出しない。失われるのは古い方のクリップで、Slackへは成功として返る。タイトルが取れなかった記事はすべて `untitled.md` に集まるため、同じホストでは特に上書きが起きやすい。
- **再送時の短絡を失う。** Slackが同一イベントを再送すると、毎回 取得・要約・保存をやり直す。外部APIの呼び出しとAIの課金がその分増え、GitHubには内容が同じコミットが積まれることがある。Slackへの返信自体は `postSlackMessage` の冪等キーで二重投稿を防いでいる。
- 記事のタイトルが変わると、次のクリップで別のファイルが増える。古いファイルは残る。
- 保存したMarkdownから要約を再取得できなくなる。過去のクリップの要約は残らない。
- `putGitHubFile` が409を返した場合は、保存先を読み直してURLを得て、手元の要約でそのまま返信する。書き込みの内容は先に書いた側のものになる。
- ファイル名にはタイトル由来の記号（`&` `#` `!` `（）` など）がそのまま残る。GitHub Contents APIへはパス構成要素ごとにURLエンコードして渡す。
